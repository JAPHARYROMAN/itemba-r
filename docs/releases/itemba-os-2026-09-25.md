## Dependency remediation

The initial production dependency audit reported five affected frontend packages
(including critical Next.js advisories) and eleven backend packages. Refreshing
the supported version ranges and lockfiles removes those findings. The frontend
and backend production audits both returned zero known advisories locally. The
website is also part of the production compose deployment and its Next.js 15
version range has been patched without moving it to Next.js 16.

The mail dependency moves from Nodemailer 8 to 9.1.1. Its relevant breaking change
is certificate validation for remote content; ITEMBA's mail service uses ordinary
SMTP and in-memory attachments. Do not disable TLS verification to make a provider
work. See the [maintainer changelog](https://github.com/nodemailer/nodemailer/blob/master/CHANGELOG.md).

ExcelJS's UUID dependency is scoped to UUID 11.1.1 or later in the 11.x range.
ExcelJS only uses its CommonJS `v4()` interface, which remains available; workbook
export and conditional-formatting round trips must pass with the final installed
dependency set. This avoids the audit tool's proposed downgrade of ExcelJS.

CI now rejects high/critical production dependency advisories in the backend,
frontend and website. This audit gate is required by the deployment runtime job.
It complements application tests; a zero advisory count is not a security audit.

## Opening position

The read-only audit was against the **working local database**, not production:

- Two companies need accounting currency/profile review.
- Two posted journal lines refer to missing, deleted or cross-company accounts.
- One nonzero cash account lacks a ledger mapping.
- One stock valuation requires reconciliation; employee readiness also needs review.

Opening approval is false. Do not invent account mappings, stock adjustments or
opening journals. Preserve existing live data unless an approved import plan says
otherwise. Repeat the audit against an authorised production copy, agree the
release scope and obtain business-owner sign-off on control totals.

## Deployment sequence and outstanding gates

1. Complete all required CI checks for the exact candidate, review the changes and
   merge. The production workflow also requires a successful **main push CI run
   for that exact merged SHA**, including its main-only deployment/image jobs.
   The advisory Windows process-timing job had two failures on the first candidate;
   protected Windows verification passed. The advisory failures are not silently
   reclassified as passes.
2. Build with `NEXT_PUBLIC_ITEMBA_OS_ENABLED=true` in the approved deployment
   configuration. This is a build-time setting; restarting an old image does not
   enable the desktop. Production and staging compose default to false, and the
   deployment validator now checks both explicit settings reach the build without
   changing backend permissions.
3. Deploy the same final candidate to staging with approved roles and representative
   data. Complete purchase/payment/reconciliation, sales/collection and payroll/payment
   acceptance through the UI. Finish date-picker, printing, screen-reader, mobile,
   concurrent-device and six-populated-window performance checks. Records forms
   currently retain in-memory navigation warnings rather than server draft recovery.
4. Verify the live host configuration and production-scale backup. Restore database
   **and uploaded files/object storage** into a separate recovery environment;
   confirm retention, off-server copy, alert delivery, recovery ownership and timings.
   Local restore evidence does not certify these gates.
5. Capture the previous deployable image and configuration. Rehearse old-image
   compatibility/rollback against the migrated production copy and agree the traffic
   cutover and recovery decision before the manual production deployment.

Production SSH target/access and business data acceptance remain external inputs.
No production deployment has been performed by this release-preparation pass.

Automatic approval review rejected starting the isolated frontend on port 3109
with “blocked by policy.” The existing frontend on port 3009 was reviewed instead;
this does not satisfy browser acceptance against the isolated financial fixture.
