# Completeness Critique — Kaunta / Itemba POS Reform Plan

Everything below was verified against main @ 76597c47 where a file is cited. Ordered: (A) things the plan gets wrong or contradicts, (B) verified codebase landmines the specs miss, (C) missing coverage per requested checklist, (D) v1 scope cuts.

---

## A. Contradictions and internal spec conflicts

**A1. The Leo/Daftari module has no spec — and it is a load-bearing dependency.** Sales spec item #9 ("Foleni merge into Leo pending section — rides Leo spec's screen") and the direction's most distinctive surface (ruled-line book, tally row, "Zimetumwa 12 · Mkononi 3" reconciliation, staleness stamp, retry) have no build spec, no i18n keys, no size estimate, and — critically — **no storage design**. The direction promises "offline shows local tally + last-known day total," but neither exists anywhere today: successful outbox rows are deleted on sync (`removePendingMobilePosLiteSale`, `frontend/src/lib/mobile-pos-lite-store.ts:196`), so sent-today count/total is unrecoverable offline after an app restart, and `my-sales-today` responses are not cached. Leo needs a persisted day-log/tally store (a per-date counter or cached my-sales-today snapshot) — which also means the IDB v4 migration list (`stocks` + `drafts` only) is **incomplete**. Mipangilio likewise has no spec (small, but it owns three back-map-relevant toggles).

**A2. Logout is deleted with no replacement.** The current header has a logout button (`mobile-pos-lite.tsx:1936–1946`, key `logOut`). The home screen (which hosts the header) is deleted, and the direction's Mipangilio list is explicitly "Nothing else" — logout appears nowhere in the new shell. Shared/reassigned phones and shift changes need it. Add logout (and probably the rep-name/branch identity line) to Mipangilio.

**A3. pushState URL shape is unresolved and one of the two options breaks offline.** The sales spec says "history.pushState pseudo-routing" with no URL shape; the purchases spec uses hashes (`#manunuzi/historia/:id`). This must be mandated **hash-only (or state-object-only)**: the SW navigate allowlist is an exact-path Set (`frontend/public/mobile-pos-sw.js:2,21` — `POS_ROUTES.has(url.pathname)`), so a path-shaped pushState (`/mobile-pos/malipo`) makes any offline reload/PWA-relaunch dead-end, and an online hard refresh 404s (no such Next route). Also unspecified: cold-boot deep-link handling — manifest shortcut "Stoo" needs a hash the boot sequence reads, but the sales spec's boot logic only says "boots into Mauzo."

**A4. i18n key naming is inconsistent inside the inventory spec and duplicated across specs.** Inventory §2–3 reference dot-namespaced keys (`stoo.freshNow`, `stoo.lastSeen`, `stoo.noPrice`, `hesabu.progress`, …) while its own §4 table defines flat keys (`stockFreshNow`, `countProgress`). The existing catalog is a flat `keyof` union (`pos-i18n.ts:199`) — dot names break typing; pick flat and fix §2–3. Across specs, "Jaribu tena" exists three times: `retryThisSale` (sales), `tryAgain` (purchases, claimed as "define once, shared"), `stockRetry` (inventory) — consolidate to one. Also the direction says "~40 new keys"; the specs actually total ~93+ (26+25+42, before Leo/Mipangilio keys, which are missing entirely). The direction under-scopes i18n by >2×.

**A5. Historia (purchase history) is scope the direction never approved.** The direction's screen map, backend list (§7 "all pre-scoped"), and phase plan contain no purchase history, no `GET /mobile-pos-lite/purchases`, no detail screen. The purchases spec adds a full list+detail+endpoint (2M+2S of work) and hand-waves its phase ("any time after Phase 2"). Either amend the direction or cut it (see D1). It also softens the direction's security stance: "no cost/value fields, ever — rep phones get stolen" becomes "manager phones show 30–90 days of buying costs," and the kikaratasi draft **stores typed unitCosts unencrypted in IDB for 48h+**. Terminal binding is per-device, not per-glance — a stolen unlocked manager phone exposes cost data. If accepted, say so explicitly as an owned risk; right now the direction and purchases spec contradict each other.

**A6. Stoo slab contradicts the slab law and has an undefined data dependency.** Sales spec §1.2: "Exactly one primary verb per screen… disabled, never hidden." Inventory §2 step 6: rep-view Stoo has *no* verb and shows "day-total" — a number owned by Leo that requires network (`my-sales-today`) and has no offline source (see A1). Define what the slab shows on Stoo/Leo offline, and reconcile the "never hidden" rule.

**A7. Hesabu preview variance baseline is ambiguous.** Server systemQuantity is `quantityOnHand` (correct), but Stoo rows display `available = onHand − reserved`. The review step says "preview variance vs the snapshot quantity" — must be pinned to `quantityOnHand`, or a branch with reservations shows preview variances that systematically disagree with server-returned truth, teaching managers to distrust the review screen.

**A8. Stale-Stoo "dot only" state violates the plan's own color-independence rule.** Inventory §2: >24h stale rows show status **dot only — no word**. Everywhere else the plan insists color is never the sole channel (dot+word, counted pill "numbers are the literacy-safe channel"). A grey/green/brass/red dot alone is exactly the imperceptible-on-720p signal Rejected #12 bans. Keep the status word, drop only the quantity.

## B. Verified codebase landmines the specs miss

**B1. IDB v4 downgrade bricks old cached shells — the plan's own "old shells keep working" guarantee breaks.** `openDatabase()` opens with hardcoded `DB_VERSION = 3` (`mobile-pos-lite-store.ts:56,66`). Once any Phase-4 shell upgrades a phone's DB to v4, an older SW-cached shell (SW update lag is explicitly expected) — or a rollback deploy — calls `indexedDB.open(name, 3)` against a v4 database and gets **VersionError**: bindings, catalog, outbox all unreadable; the POS dead-ends at activation. Neither spec mentions this. Fix before v4 ships: open version-less (or catch VersionError), feature-detect stores, and make the *v3→v4-capable* store code ship at least one release before anything writes v4. Also: both specs each describe "the v4 migration" for their own store — state explicitly that **one** v4 upgrade (Phase 4) creates both `stocks` and `drafts`.

**B2. Offline cold start almost certainly dies at the AuthGate, above the component the characterization tests cover.** `(dashboard)/layout.tsx` AuthGate: offline, `/api/auth/me` and `/api/auth/refresh` both throw (SW never touches `/api/*`), `setUser(null)` (`auth-context.tsx:~100`), and the effect redirects to `/login?from=/mobile-pos` — a route that is **not** in the SW allowlist, so the rep lands on the browser offline page. Characterization test #4 (RTL, component-level) will pass while the real phone fails. The plan needs (a) an end-to-end on-device offline cold-start test through the auth layer, and (b) likely an offline grace path (cached-user snapshot, or AuthGate skipping the redirect when offline + a POS binding exists). This may be a live production bug today; either way the plan's central promise ("offline is Tuesday") currently rests on an unverified layer.

**B3. Queued CASH sales × stock counts double-count shrinkage.** Field-realistic: manager counts at close of day while a rep's phone still holds queued CASH sales. The count captures the physically-sold (already-gone) stock as variance; the queued sale then syncs and decrements again → stock understated by the queued quantity. Related smaller window: wrapper reads `systemQuantity`, then create→submit→approve→post — a sale posting in between makes the posted adjustment wrong if the core adjustment applies set-to-counted vs delta differently than assumed. Minimum: document which semantic `StockAdjustmentsService.post` uses, and add pre-count guidance/gating ("Tuma Sasa before TUMA HESABU" — the client can check its own outbox; it cannot see other terminals', so at least warn when local queue count > 0, and note the cross-terminal case as accepted).

**B4. `POS_ONLY_PERMISSIONS` is not "untouched-safe."** The set is exactly `{'mobile_pos_lite.use'}` (`(dashboard)/layout.tsx:48`). Both specs assert "isPosOnlyUser redirect untouched," but adding `mobile_pos_lite.stock_count` (and `.purchase`) creates a user class — phone-only branch managers — who are *not* classified POS-only and get the ERP shell. Decide: either add `.purchase`/`.stock_count` to the set (POS-only managers exist) or document that manager grants intentionally imply desktop access.

**B5. Seed changes don't reach existing deployments by magic.** Seeding is upsert + `rolePermission.createMany({skipDuplicates})` (`seed.ts:2308,2336`) — re-running the seed adds `mobile_pos_lite.stock_count` to the *seeded* roles, but the plan must state that (a) the deploy pipeline actually re-runs the seed (CI note "seed-admin variables" suggests it exists — confirm), (b) custom/cloned roles created in prod won't get it (office grants manually), and (c) whether `user.permissions` in `sessionPayload` (service:1356) is DB-live per request or token-cached — if token-cached, managers need re-login before `stockCountsEnabled` appears.

**B6. The Phase-1 font change is app-wide, not POS-scoped.** The Google Fonts `@import` at `globals.css:1` styles the entire ERP. Replacing it with `next/font/local` requires wiring the font class/variable at the **root layout** and touches every dashboard page's rendering — this is a whole-app regression surface smuggled into a "near-zero risk POS PR." Split it out, subset Inter (latin, the 4–5 used weights only — the current import pulls 8 variants), and QA the desktop app too.

**B7. SW cache grows forever.** `CACHE_NAME = 'itemba-mobile-pos-lite-v1'` with `cache.put` on every `/_next/static/` fetch and no eviction (`mobile-pos-sw.js:1,30`). Five phases of frequent deploys = unbounded hashed-chunk accumulation on 8–16GB phones that are already storage-starved (the plan's own "low-end storage discipline"). Add activation-time cleanup of entries not referenced by the current build, or a versioned cache name — while preserving the no-API-cache invariant.

**B8. Small verified nits.** (i) The direction's radius values (0.875/1.25/1.75rem) differ from the shipped `--aurora-radius` scale (tailwind `aurora: 0.625rem` etc.) — fine as `.pos-shell` overrides, but say so, since Tailwind `rounded-aurora` classes compile to the *config* values, not the vars: any POS markup using `rounded-aurora*` utilities will NOT pick up the override. Audit which mechanism the POS actually uses. (ii) `ease-aurora` exists (`tailwind.config.ts:187`) — keyframe claim checks out. (iii) `notes` already exists on the purchase DTO — checks out. (iv) Session structured-clone does persist `purchasesEnabled` despite the missing type field — inventory spec's claim verified; but note pre-upgrade cached sessions lack `stockCountsEnabled`, so a manager's first offline cold-start after upgrade hides ANZA KUHESABU until one online session refresh (acceptable; document it).

## C. Missing coverage (the requested checklist)

**C1. Migration strategy — code is phased, users are not.** No pilot/canary mechanism exists: Phase 2 (boot-into-Mauzo, deleted home, new nav) flips every terminal at once via deploy, to low-literacy users who cannot self-help, with no kill switch. The infrastructure for per-terminal rollout already exists (terminal config + `configVersion`): add a `uiVersion`/pilot flag on the terminal so 1–2 pilot branches run the new shell for a week per phase while the old component stays mounted behind the switch. Also missing: an explicit statement that the old `screen`-state component and new router coexist in the bundle until Phase 3 sign-off, and a rollback rehearsal (which B1 currently makes dangerous).

**C2. Real-device rollout/testing — one test named, a matrix needed.** The plan names exactly one device test (popstate × QR login). Missing: a device matrix (1–2GB Android Go, 720p LCD, Chrome + installed-PWA WebView contexts); keyboard-wedge scanner hardware regression (Enter-key handling through the new search input and slab keyboard-collapse); `navigator.vibrate` requires user activation in modern Chrome — fine for tap-driven stamps, but verify the queued-sync path never vibrates outside a gesture; `navigator.share` per-device behavior; Android **system font scale** at 1.3–2× (does 40px Display + Swahili at 320px wrap the slab? the "frozen at 320px" rule ignores OS font scaling); gesture-nav vs 3-button nav; TalkBack pass; Data Saver / 2G throttling profiles; and a structured UAT week with actual reps plus native-speaker review of the ~93 new Swahili strings (several are new coinages — "kikaratasi", "Zaidi ya rekodi" — that deserve field validation). B2's auth-layer offline cold start belongs at the top of this matrix.

**C3. Performance budget — the direction says "genuinely fast," no spec makes it falsifiable.** Missing numbers: cold-boot-to-sellable target on a reference device (suggest ≤3s warm, ≤5s cold on a Tecno Spark-class phone), tap-to-cart-update latency (≤100ms), a JS budget for the `/mobile-pos` route (the split into screens should come with a bundle ceiling and a check in CI), and — most concretely — **the 1500-row Stoo list has no virtualization plan**. 1500 × 56px rows with photo tiles will jank/OOM on the target hardware; mandate windowing (or render-on-filter with a hard cap). Image bytes: tiles fetch `/api/backend/products/:id/image` — is there a thumbnail size, or do 64px tiles pull full uploads through the cookie proxy on metered data? No payload budget for `GET /stock` (~200–400KB every ≤10min tab-open at 1500 items; consider ETag/304). None of this is designer vanity — it's the direction's own "state of the art = fast on low-end Android" made testable.

**C4. Accessibility — reduced-motion is covered; nothing else is.** Missing: focus management for the pseudo-router (pushState changes announce nothing to TalkBack — each screen change needs focus reset to the screen title or an aria-live announcement); bottom-sheet (tray, reconnect prompt, rejected-sale ritual) focus trap and scrim dismissal semantics; aria labels for the duotone icon chips, the counted sync pill (keys exist — good), the tally row, and the decorative stamp (`aria-hidden`); contrast audit of `--aurora-text-secondary` `#475569` on the warm paper `#FAF7F0` at Label size; and A8's color-only stale state. One a11y acceptance pass per phase should be a review gate like the four-color law is.

**C5. PWA/service-worker implications.** B1, B2, B7 above, plus: manifest identity change (theme_color teal→paper, new maskable icon) is safe, but **shortcuts deep-links need the hash-boot handling from A3**; `start_url`/`scope` untouched — good; the plan should state the Android-only assumption explicitly (vibrate, install flow, and share all differ on iOS — currently implicit); and the "old shell keeps working" claim should get an explicit compat test: previous release's cached shell against the new API in CI or staging, per phase.

**C6. Backend contract risks not yet owned.** (i) `posErrorMessage()` regexes over free-text English — any backend copy edit silently breaks the Swahili mapping; add a backend test asserting the exact strings the frontend matches (cheap tripwire), and put real error codes on the audit track with a date. (ii) `GET /purchases` `status: COMPLETE = GRN POSTED` — define what an APPROVED-but-not-POSTED GRN shows (currently falls into INCOMPLETE; fine, but say it). (iii) `notes contains` marker filters are load-bearing for idempotency *and* now for history filtering — protect the marker format with a shared constant + test, since two features die if anyone "cleans up" notes. (iv) `take: 1500` Stoo truncation is silent — return a `truncated: true` flag so the client can show "list incomplete" instead of lying by omission.

**C7. No telemetry, no feedback loop.** The plan repeatedly says "watch" (manager boot friction, haptic variance, field demand for earcons/last-module memory) with no instrument to watch *with*. Minimum viable: server-side counters (rejected-sale rate per terminal, queue age at flush, count variance magnitudes, session refetch failures) — all derivable from existing writes — plus a lightweight client error log (even a ring buffer surfaced in Mipangilio for supervisors). Otherwise every "pre-approved follow-up" trigger is unmeasurable.

**C8. Small missing definitions.** Keyboard-collapse should key off `visualViewport` resize, not focus/blur alone (Android keyboard dismissal without blur is common). `itemba-pos-theme`/`itemba-pos-haptics` need read-time validation like `readStoredLang` has. Auto-peek "once per mount" vs "once per session" — sales spec says both ("first add of a session", "once per mount"); pick one. Receipt `toLocaleString('en-GB')` timestamps in a Swahili-first app — fine, but decide deliberately.

## D. Scope: cut from v1

1. **Historia list + detail + `GET /purchases` (purchases spec §3.3–3.4, §5.2)** — never in the direction (A5), serves the secondary user's *review* need which the office desktop already covers, adds a cost-data surface on phones and ~2M+2S of work. Cut whole, or keep a 10-row list and cut the detail overlay. This is the single largest unapproved addition.
2. **Usiku dark mode day one** — forced-light default means near-zero day-one users; it doubles the visual QA matrix across ~10 screens × 5 phases. Ship the token table (cheap) but make Usiku a Phase-5 toggle-on after Mchana QA, or cut the toggle to a follow-up. (The direction insists both ship; this is the place to push back — the sunlight argument that made Mchana default is the same argument that makes Usiku near-worthless in the field.)
3. **Kikaratasi reconnect-prompt state machine** — keep the *auto-persist crash insurance* (cheap, high value), cut the reconnect bottom-sheet/expiry/discard ritual from v1; on reopen, Pokea simply restores the draft into the form and the manager taps POKEA. Same safety, one fewer state machine; revisit if managers actually lose slips.
4. **`?low=true` query param** — specced-and-tested-but-unused; drop until the notification use-case exists (it's an S, but it's also contract surface to maintain).
5. **Manifest shortcuts** — depend on unbuilt hash-boot handling (A3); trivial to add later, nonzero to get right now.
6. **Decimal (3dp) CountInput** — if the catalog's stock items are effectively integer-unit (verify), ship integer counting v1 and match sales' 1–9999 mental model; decimals return with weighed-goods support.
7. **Keep** (explicitly *not* cuttable despite temptation): haptics, the MUHURI, the tally/Daftari identity, blind counting, the rejected-sale ritual — these carry the concept's value; and Phase 0 characterization tests, extended per B2 to an on-device offline E2E.

## Top five actions before this becomes the official plan
1. Write the Leo/Daftari (+Mipangilio) spec, including the missing local day-log storage and logout (A1, A2).
2. Fix the IDB version-open hazard and define the single v4 migration + rollback story (B1).
3. Prove or fix offline cold start through the AuthGate on a real device (B2).
4. Mandate hash-only routing and cold-boot hash handling (A3).
5. Add a per-terminal pilot flag and a measurable performance budget with Stoo virtualization (C1, C3).
