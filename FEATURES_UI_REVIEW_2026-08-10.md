# ITEMBA-R — Features & UI Review

**Date:** 2026-08-10 · **Baseline:** commit `50e64841` (main) · **Scope:** the full application — Next.js frontend (225 dashboard pages across 32 sections, Next 16 / React 19 / Tailwind), NestJS backend (151 modules), Prisma schema (328 models)

## Scope & method

Eleven parallel reviewers each covered one functional area (shell/auth/admin, dashboard & reports, operations/inventory, procurement, sales/CRM/mobile POS, finance & accounting, HR, compliance/approvals/security, platform & multi-company, the Westsides vertical, and an app-wide UI-consistency sweep). Every finding required reading the actual code and cross-checking frontend API calls against the backend controllers/DTOs; claims carry `file:line` evidence. I independently re-verified the three findings that anchor the executive summary (PUT-vs-PATCH, compliance tax paths, HR sidebar permission codes) — all confirmed.

**Out of scope:** the `website/` folder (separate single-page marketing site); deep accounting-math correctness (already covered by the earlier GL/money and backend-logic audits — this review focuses on feature completeness and UI); runtime/browser testing (this is a static, code-grounded review — line numbers are as of the baseline commit).

## Executive summary

The app is far bigger and deeper than most ERPs at this stage — 225 working pages, a genuinely good design system ("Aurora": tokens, Modal/ConfirmDialog/StatusBadge/ResponsiveDataTable, three-mode theming with no FOUC), a consistently guarded and validated backend, and several truly production-grade workflows (Records Book lifecycle, customer-payment allocation, the GRN receiving wizard, Mobile POS Lite's offline/idempotent sale path, the Roles permission matrix, the Tax Cockpit, payroll's bilingual payslips).

But the review's central finding is this: **a large slice of the UI surface — roughly a fifth of pages — does not actually work against the backend, and the app hides it.** The defect class is broken frontend↔backend contracts: wrong URL paths (9 of 20 compliance tax pages, HR documents, automation dashboard, restore-tests, 3 catalog reports), wrong HTTP verbs (PUT vs `@Patch` breaks Save on 8 finance pages; POST vs `@Patch` breaks approve/reject across HR), payloads the backend's strict ValidationPipe must reject (at least 14 HR create forms), response-envelope mismatches (refunds, financial statements, data-isolation pages that crash on real data), and identifier mismatches (saved report views can never save; sales commissions require permission codes that were never seeded; the HR sidebar demands `hr.*` permission codes that don't exist, hiding ~20 nav items from every user).

What makes this dangerous rather than merely annoying is the **silent-failure epidemic**: dozens of pages use `.catch(() => {})` or ignore `res.ok`, so a dead endpoint renders as a friendly empty state and a failed save closes the modal as if it succeeded. Broken features look healthy; QA by clicking around cannot catch them. Two findings are outright data-integrity risks: the Westsides daily cash close collects counts and "supervisor sign-off" but persists nothing, and RFQ "Cancel" toasts success while writing nothing.

The pattern behind almost every finding is **two coexisting generations of code**. The newer generation (automation rules/runs, group-control, customer statements/payments, approvals decisions, employees, quotations/proformas) documents its backend contract, paginates, gates permissions per action, and surfaces errors. The older scaffold generation hand-rolls tables and modals, truncates silently at 20 rows, renders raw UUIDs, and swallows errors. The fix strategy is therefore mostly *convergence*: the good pattern already exists in-repo for every problem found.

**Totals: 209 findings — 19 Critical, 45 High, 83 Medium, 62 Low.** The backend consistently comes out ahead of the frontend: most gaps are missing or mis-wired UI over capability that already exists and is well-guarded server-side.

## The critical list — what to fix first

1. **Compliance tax administration is entirely dead** — 9 of 20 compliance pages call `compliance/tax-*` and `compliance/exports`; the backend serves `tax/types`, `tax/rates`, … and `data-exports`. Every list shows a false empty state; every action 404s. (Compliance §1)
2. **HR legacy forms can never save** — ≥14 create forms post payloads the global `forbidNonWhitelisted` ValidationPipe rejects; leave approval is triply dead (no Submit button, wrong status check, wrong verb); the HR documents page 404s; and the HR sidebar's nonexistent `hr.*` permission codes hide ~20 items from everyone. (HR §1–4)
3. **Finance edit is broken on 8 pages** — modals send `PUT`, controllers register only `@Patch`; every "Save Changes" 404s and most close as if they succeeded. Same family: refunds' credit-note dropdown can never populate; the financial-statements viewer can't parse what the backend stores; fiscal-year/period delete hits endpoints that don't exist. (Finance §1–4)
4. **The approval engine is an island** — nothing in the ERP creates approval requests, no UI defines workflow steps, so the entire approvals suite processes a queue that can never fill. (Compliance §2, §4)
5. **Procurement's sourcing middle is inoperable** — supplier quotations and bid comparisons have no create UI, "Approve & Award" awards nothing, and RFQ "Cancel" is a silent no-op with a success toast. (Procurement §1–3)
6. **Saved report views can never save** — the runner posts catalog string ids where the backend requires `ReportDefinition` UUIDs; the whole saved-views panel including default-view auto-apply is dead. Scheduled-report snapshots contain no report data and can't be downloaded. (Dashboard §1, §3)
7. **Platform pages call nonexistent endpoints** — the automation dashboard (`business-automation/summary`) and restore-tests pages always render empty; the disaster-recovery checklist cites restore tests as compliance evidence — a false all-clear. API clients/keys have no provisioning UI at all. (Platform §1–3)
8. **Sales commissions are dead for every seeded role** — the controller requires `sales_orders.*` permissions that no seed defines, and the page is orphaned from the nav with a 404 breadcrumb. (Sales §1–2)
9. **Westsides daily close persists nothing** — cash counts, variances, and "supervisor sign-off" live only in React state; a financial control with no record and silent data loss. (Westsides §1)
10. **Data-isolation pages crash once data exists** — both list pages map over the pagination envelope object. (Compliance §3)
11. **Auth dead ends** — an account with 2FA enabled cannot log in through the web UI, and there is no password-reset page despite complete backend support and whitelisted routes. (Shell §1–2)
12. **The silent-failure epidemic** — pervasive `.catch(() => {})` / unchecked `res.ok` is what let items 1–10 ship unnoticed; fixing it is what keeps them from regressing. (every area; Cross-cutting)

## Recurring themes

1. **Broken FE↔BE contracts are the #1 defect class.** Wrong paths, wrong verbs, wrong payload field names, wrong response-envelope assumptions, wrong identifiers, and query-param drift (`runId` vs `payrollRunId`, dead `search` params). The two sides evidently shipped from different specs with no contract test between them. A route/DTO contract test (frontend calls enumerated and asserted against the NestJS route table) would have caught nearly every Critical finding in this report.
2. **Failures are invisible by design.** The scaffold generation swallows errors at both load (`catch(console.error)` → false empty state) and mutation (unchecked `fetch` → modal closes, list reloads). The newer generation's pattern (api-client + `res.ok` + toast/ErrorState with retry) exists and works — it needs to become mandatory.
3. **Two generations, one app.** Every area review independently described the same split: a polished Aurora-era generation and a legacy scaffold generation (hand-rolled tables/modals, hardcoded light-theme grays, no pagination, no permission gating). The report's per-area findings are largely a map of which pages still await the migration.
4. **Workflow chains with missing middles.** Requisition→PO conversion, quotation/bid-comparison creation, approval-request creation and step definition, leave submit→approve, employee termination/transfer/disciplinary approvals, price-list items, evidence-pack items, backup trigger/restore, bank-reconciliation manual matching. The backend implements each chain end-to-end; the UI exposes the ends but not the middle, so documents dead-end in intermediate states.
5. **Backend capability with zero UI surface.** Confirmed orphan modules include: 2FA + password reset, `profit`, `customer-statements` (finance-side), `tax-anomaly-detection` (page-level), `expense-categories` admin, `cache-management`, `data-exports`, `groups` CRUD, `sales-channels`, `mobile-sessions` (incl. the revoke security control), `offline-sync` conflict resolution, `user-dashboard-preferences`, stock-ageing & branch-profitability reports, api-clients/api-keys, approval steps/comments/detail, GRN-per-PO filtering. The product is meaningfully smaller in the UI than in the API.
6. **Navigation hides real features.** Sidebar groups for automation, background-jobs, api-gateway, data-isolation, and sales/commissions are placeholder comments; the Tax Cockpit, OSHA registrations, disputes, and disciplinary pages live only in the command palette; HR nav permission codes match nothing. Meanwhile some links that do exist 404 (`/operations/procurement/grns`, `/sales` breadcrumb, three settings-catalog routes) or drop their promised filters (`?create=1`, `?severity=HIGH`, "pre-scoped" product links).
7. **Silent 20-row truncation.** Backends default to `limit=20` and many pages neither pass paging params nor render a pager — CRM (5 pages), tasks/alerts (3), notifications, security (4), approvals/requests, plus 50/100-row caps across integrations and Westsides. Stat tiles computed from the truncated page compound it (two-factor adoption, commissions totals, integrations dashboard).
8. **Raw UUIDs as UX.** Required free-text UUID fields (payroll period, leave type, sales order, posting rule, report definition, package/customer IDs, document owner) and UUID table columns (GRN supplier, credit profiles, supplier statements, security sessions/events, accounting locks, backup runs) make whole workflows operator-hostile or unusable, even where the data to resolve names is already loaded.
9. **A11y is strong in the kit's core, absent at its edges.** `Modal` and `ProductPicker` are exemplary; but `forms.tsx` renders labels with no `htmlFor`/`id` association (every form field in 126 files), `ConfirmDialog`/`DetailDrawer` have no focus trap and can layer under `Modal`, and the scaffold generation's hand-rolled modals have no dialog semantics at all.
10. **Formatting and theming drift.** Three number/date locales (`en-GB`/`en-US`/`en-TZ`) plus hardcoded "TZS" labels over mixed-currency sums; dark mode depends on a ~250-rule `!important` compat bridge; several Westsides/record-book pages hardcode the opposite theme and are unreadable in the default light mode; ~220 pages share one browser-tab title; no unsaved-changes protection exists anywhere.

## Recommended fix waves

- **Wave 1 — Reconnect the wires (Critical, mostly small diffs).** Fix paths/verbs/payloads/envelopes: compliance `tax/*` paths + verbs; finance PUT→PATCH (8 pages) and the refunds/financial-statements/fiscal-period parsers; HR DTO alignment + POST→PATCH + `hr/documents` path + sidebar permission codes; saved-views id model; automation-summary and restore-tests endpoints (build or remove); commissions permission seeds; data-isolation envelope crash; RFQ cancel (support status or remove the action). Each is verifiable with a contract test.
- **Wave 2 — Make failure visible.** Adopt the api-client + `res.ok` + toast/ErrorState-with-retry pattern everywhere; ban `.catch(() => {})` and unchecked mutations via lint rule; route all fetches through `lib/api-client.ts` (its 401-refresh already exists). This is the guard rail that keeps Wave 1 fixed.
- **Wave 3 — Complete the workflow middles.** Supplier-quotation & bid-comparison capture; requisition→RFQ/PO conversion; approval-engine integration into at least PO/expense/payment flows + step-definition UI; leave submit/approve; termination/transfer/disciplinary approval surfaces; price-list items; evidence-pack items; backup run-now/restore; bank-reconciliation manual matching; 2FA challenge + password-reset pages.
- **Wave 4 — Surface hidden capability.** Sidebar entries for the orphaned sections and pages; notification bell with `unread-count`; per-employee detail tabs; api-clients/keys admin; mobile-session revoke; supplier-statements generate; generated-documents download; groups CRUD.
- **Wave 5 — Systemic UX/a11y hardening.** `forms.tsx` label association + `aria-invalid`/`aria-describedby`; ConfirmDialog focus trap + z-index; pagination defaults on every list; entity pickers replacing UUID fields; per-page `document.title`; unsaved-changes guard; one formatter lib + one locale + real currency codes; retire the dark-mode `!important` bridge by finishing the scaffold-page migration; converge on ConfirmDialog (no native `confirm()`/`alert()`).

# Per-area reviews


## Area: Shell, Auth & Admin

The shell (sidebar/topbar/auth gate), auth pages, and admin surfaces are genuinely functional: cookie-based session handling with single-flight silent refresh is well engineered, error boundaries exist at every level, and the Roles page is a complete, design-system-faithful CRUD workflow with a permission-matrix editor. Quality is uneven, though: the Users and Notifications pages predate the design system (hand-rolled modals, native `confirm()`, raw error text), and several backend auth capabilities (2FA, password reset, company access) have no UI at all — including two dead-end flows visible to end users.

### Findings

- **[High] 2FA is implemented in the backend but unusable — and login dead-ends on it** — `backend/src/modules/auth/auth.controller.ts:168-236` exposes the full TOTP flow (`2fa/setup`, `verify`, public `2fa/challenge`, `disable`, backup codes), but no frontend code calls any of it; on `requires2FA` the login page just shows "Contact an administrator" (`frontend/src/app/(auth)/login/page.tsx:94-97`) with no code-entry UI, and `frontend/src/app/(dashboard)/security/two-factor/page.tsx:80` tells users to enable 2FA "from their profile settings page", a page that does not exist. Any account with 2FA on (e.g. via enforced security policy) cannot sign in through the web UI.
- **[High] Password reset has no UI surface** — backend `POST /auth/password-reset/request` and `/reset` are public and complete (`auth.controller.ts:120-146`), and `frontend/src/contexts/auth-context.tsx:9` even whitelists `/forgot-password` and `/reset-password` as public paths — but those pages don't exist and the login page has no "Forgot password" link. Locked-out users have zero self-service recovery.
- **[High] Design-system form fields are not accessible** — `frontend/src/components/ui/forms.tsx:56-70` renders `<label>` with no `htmlFor` and inputs get no `id`, `aria-invalid`, or `aria-describedby` linking to the error text, so every `FormInput`/`FormSelect`/`FormTextarea`/`DateInput` in the app is unlabeled for assistive tech and errors aren't announced. This is a systemic a11y gap baked into the primitives themselves.
- **[Medium] Settings directory links to routes that 404** — the backend settings catalog marks `/business-units` (`backend/src/modules/settings-catalog/catalog.ts:61`), `/business-units/licenses` (`:71`), and `/retention` (`:419`) as `BUILT_IN`, but no such pages exist anywhere under `(dashboard)`; the "All settings directory" renders them as clickable "Open" rows.
- **[Medium] Topbar Quick Create deep links are dead parameters** — "New Sales Order" and "New Purchase Order" navigate to `...?create=1` (`frontend/src/components/layout/topbar.tsx:28-38`), but neither target page reads `useSearchParams` or the `create` param, so the user just lands on the list view with no create form opened — a misleading "quick action".
- **[Medium] Notifications page silently caps at 20 items with no pagination and no error state** — backend defaults to `limit = 20` (`backend/src/modules/notifications/notifications.service.ts:52`), the page never passes page/limit and has no pager (`frontend/src/app/(dashboard)/notifications/page.tsx:49-69`); the unread badge is computed by filtering that first page, the dedicated `GET /notifications/unread-count` endpoint is unused, and load failures are `catch(console.error)` — rendering as a false "No notifications".
- **[Medium] No notification indicator in the shell** — the topbar has search, quick-create, theme, and the user menu but no bell/unread badge (`frontend/src/components/layout/topbar.tsx`), despite the backend's `unread-count` endpoint; users must proactively visit `/notifications` to see approvals or critical alerts.
- **[Medium] Whole built sections are unreachable from the sidebar** — pages exist for `/automation` (+rules/runs), `/background-jobs` (+queues), `/data-isolation` (+issues/test-runs), `/api-gateway/logs`, and `/sales/commissions`, but the NAV tree has only placeholder comments for them (`frontend/src/components/layout/sidebar.tsx:1104-1106`); they're orphans reachable only by URL (the settings catalog links to `/automation`, deepening the inconsistency).
- **[Medium] Users page bypasses the design system it sits next to** — hand-rolled modal with no focus trap/ESC/aria (`frontend/src/app/(dashboard)/users/page.tsx:135-225`), native `confirm()`/`alert()` for deactivation (`:485-504`), a local duplicate `StatusBadge` (`:44-56`), and hardcoded slate/blue palette — while the sibling Roles page uses `Modal`, `ConfirmDialog`, `ErrorState`, `EmptyState` throughout. `RolesModal.tsx` has the same raw-overlay problem (no ESC, no focus trap).
- **[Medium] Users page has no permission-denied or friendly error state** — it fetches unconditionally and renders the raw failure (`HTTP 403`) as plain red text (`users/page.tsx:246-250, 396-398`), whereas Roles renders a proper "You do not have permission" card (`roles/page.tsx:132-141`). Sibling pages behave differently for the same condition.
- **[Medium] `PUT /users/:id/company-access` has no UI** — the backend supports managing a user's company-access list (`backend/src/modules/users/users.controller.ts:60-61`), but no frontend code references it; admins can assign roles via `RolesModal` yet cannot manage company access without hitting the API directly.
- **[Low] ConfirmDialog/DetailDrawer lack focus management and can layer under Modal** — `ConfirmDialog` (`confirm-dialog.tsx:88`, `z-50`) and `DetailDrawer` (`detail-drawer.tsx:46`, `z-40`) have no focus trap or initial focus, and both sit below `Modal`'s `z-[1200]` (`modal.tsx:117`), so a confirm opened from inside a modal renders behind it.
- **[Low] Sidebar shows empty, dead group headers to restricted users** — a group with no `permission` of its own (e.g. Registry) renders even when every child is filtered out (`sidebar.tsx:1282-1283`), producing a header that expands to nothing for users lacking `companies.read`/`users.read`/`roles.read`.
- **[Low] Sidebar groups don't auto-expand on client-side navigation** — the expanded-set is computed once in the `useState` initializer (`sidebar.tsx:1131-1139`); navigating to a group's child via search/command palette highlights the header but never opens the group. Group toggle buttons also lack `aria-expanded` (`:1289-1306`).
- **[Low] Native `window.confirm` used for destructive settings actions** — "Reset my workspace" (`settings/page.tsx:328`), preferences reset (`settings/preferences/page.tsx:207`), and the number-consuming "Advance" action (`settings/number-sequences/page.tsx:184`) all use browser dialogs instead of the design system's `ConfirmDialog`, which the same section's sibling pages do use.
- **[Low] Settings "Include planned" toggle is inert** — the catalog contains zero `status: 'PLANNED'` entries (verified by grep of `catalog.ts`), so the toggle and the planned-disable rendering in `ShortcutCard`/`DirectoryRow` (`settings/page.tsx:608-618, 681-693`) are dead code presented as a feature.
- **[Low] PageHeader breadcrumbs use `<a>` instead of `next/link`** — `frontend/src/components/ui/page-header.tsx:27` triggers full page reloads on every breadcrumb click, unlike all other in-app navigation.
- **[Low] Signup auto-logs the user into an empty workspace** — the "Request access" flow (`(auth)/signup/page.tsx:44`) creates the account, sets cookies, and redirects to `/dashboard`, where a role-less user sees an almost-empty sidebar with no explanation that an admin must grant permissions.
- **[Low] Topbar user menu has no path to profile/preferences** — the dropdown offers only identity info and "Sign out" (`topbar.tsx:201-253`); the natural home for "My workspace settings" (`/settings/preferences`) is absent.

### Strengths

- **Session architecture is production-grade**: httpOnly cookie proxying, single-flight silent refresh with retry backoff and refresh-token-rotation awareness, a `SESSION_EXPIRED_EVENT` that cleanly bounces to `/login?expired=1` with a friendly banner, and open-redirect-safe `?from=` validation (`auth-context.tsx`, `login/page.tsx:106-119`, `proxy.ts`).
- **The `Modal` primitive is exemplary**: focus capture and restore, Tab trapping, ESC handling, `aria-modal`/`aria-labelledby`, body scroll lock, and enter/exit animations (`modal.tsx`).
- **Error-boundary coverage is complete**: `global-error.tsx` (dependency-free inline styles), root `error.tsx`, auth-scoped and dashboard-scoped boundaries, all surfacing the error digest for support.
- **The Roles page is a model admin workflow**: full CRUD, module-grouped permission matrix with filter and select-all, count summaries, system-role protections, and consistent use of every relevant design-system primitive.
- **Theming is done right at the shell level**: FOUC-prevention inline script in `app/layout.tsx`, a three-mode accessible `ThemeSelector` (radiogroup semantics), reduced-motion support threaded through skeletons and animations, and a pragmatic dark-mode compat layer in `globals.css` for legacy hardcoded classes.
- **Sidebar permission gating is consistent and thorough**, including re-validating pinned favorites against the canonical NAV tree so stale stars are hidden when access is revoked (`sidebar.tsx:1153-1165`).


## Area: Dashboard, Reports & Activity

The area spans a genuinely impressive executive dashboard (fully live Prisma-backed data via `/dashboard/executive-summary`), a governed report catalog + universal runner with lineage/data-quality/explain/export-audit sidecars, an unusually complete Records Book module (CRUD, finalize/reopen/void with reasons, trash/restore, 4-format exports with audit), plus lighter tasks/alerts/audit-log utility pages. Overall quality is bimodal: dashboard, record-book, and audit-logs are polished and complete, while the BI-governance layer (saved views, scheduled reports) is wired to a `ReportDefinition` table the catalog never references — leaving several visible features dead on arrival — and the tasks/alerts pages are a generation behind the design system.

### Findings

- **[Critical] "Save view" in the report runner can never succeed, and its saved-views list is always empty** — `reports/run/page.tsx:563-620` posts `reportDefinitionId: reportId` using catalog string ids (e.g. `finance.profit-and-loss`), but `backend/src/modules/saved-report-views/saved-report-views.service.ts:142-148` requires the id to match a `ReportDefinition` row whose ids are UUIDs (`database/prisma/schema.prisma:10586-10587`; seeds create only `RPT-*` UUID rows at `database/seeds/seed.ts:8508`). Every save 404s ("Report Definition not found") and the runner's list query (`run/page.tsx:489-517`, filtered by the catalog id) can never match a stored view — the entire "My saved views" panel (`run/page.tsx:1049-1181`) is dead in practice, including the default-view auto-apply.
- **[High] Three catalog reports point to endpoints that don't exist** — `backend/src/modules/reports-catalog/catalog.ts:431,442,453` declare apiPaths `/group-reports/sales|activity-feed|audit-trail`, but no `@Controller('group-reports')` exists anywhere in `backend/src` (grep confirms the only occurrences are in the catalog itself). `group.sales` is even featured in `PRIORITY_REPORT_IDS` ("Most useful reports", `reports/page.tsx:128-140`), so a promoted card 404s when run.
- **[High] Scheduled-report runs export only schedule metadata, and the file can never be downloaded** — `scheduled-reports.service.ts:290-309` (`buildSnapshotRows`) emits schedule code/name/dataset/timestamp rows, never actual report data; the file content is stored base64 inside `ReportRun.resultSummary` (`scheduled-reports.service.ts:150`) with no download endpoint anywhere in the backend (that line is the sole `contentBase64` reference). The UI toast "Snapshot ready: filename" (`reports/scheduled/page.tsx:262-282`) and the dispatcher email "…available for download: filename" (`job-worker.service.ts:938-941`) both reference an unreachable, contentless artifact.
- **[High] The scheduled-reports page's prominent warning banner states the opposite of actual behavior** — `reports/scheduled/page.tsx:33-37, 457-476` claims "The backend has NO scheduler… nothing runs automatically and no emails are sent on a schedule today," but `job-worker.service.ts:73,108` starts a polling loop on module init and `enqueueDueScheduledReports` (`job-worker.service.ts:863-960`) auto-claims due schedules and emails all configured recipients. Users entering recipient emails believing nothing will send are being misled into triggering real email dispatch.
- **[Medium] Saved-views and scheduled-reports create forms demand UUIDs the UI never exposes** — `reports/saved-views/page.tsx:426-441` and `reports/scheduled/page.tsx:543-569` require pasting "Report definition ID (UUID)", "Saved view ID", and "Company ID" as free text; no endpoint lists `ReportDefinition` rows (only global-search touches the table internally), so a normal user cannot complete either form. The two saved-views surfaces (admin page = UUIDs, runner = catalog ids) are mutually incompatible.
- **[Medium] Tasks, alert events, and alert rules silently cap at 20 rows with no pagination or filter UI** — backends default `limit = 20` (`tasks.service.ts:15,31`, `alert-events.service.ts:42`, `alert-rules.service.ts:12`) and support status/priority/type filters, but the pages fetch with no params and render no pager (`tasks/page.tsx:147-155`, `alerts/page.tsx:47-54`, `alerts/rules/page.tsx:152-157`). Item 21+ is unreachable with zero indication more exist.
- **[Medium] Dashboard's "Full Audit Trail →" deep-link filter is silently dropped** — `dashboard/page.tsx:1072` links to `/audit-logs?severity=HIGH`, but `audit-logs/page.tsx` never reads URL search params (severity state starts `''` at line 174), so the promised pre-filtered view opens unfiltered.
- **[Medium] Tasks/alerts pages swallow load failures into misleading empty states** — `load()` uses `.catch(console.error)` (`tasks/page.tsx:153`, `alerts/page.tsx:52`, `alerts/rules/page.tsx:156`); an API error renders "No tasks found"/"No open alerts" with no error state or retry, despite `ErrorState` existing in the design system and being used correctly by the dashboard and saved-views/scheduled pages.
- **[Medium] Universal report viewer withholds date filters from ~20 dated reports** — `reports/run/page.tsx:921-930` shows date inputs only for 7 hardcoded categories; catalog categories such as Payroll, Money Out, Daily, Trend, Movement, Profit, AR / AP, and Tax get no date-range UI even though their endpoints accept `dateFrom/dateTo` (e.g. record-book reports controller, HR reports), so those runs are unbounded and unfilterable in the viewer.

- **[Medium] Three parallel mobile POS implementations coexist** — `/mobile-pos` mounts the new locked `MobilePosLite`, while `/westsides/mobile-pos/page.tsx` and `/operations/mobile-pos/page.tsx` both mount the older `MobilePosSaleEntry`; all three share the same manifest/standalone chrome (`(dashboard)/layout.tsx:56-59`), inviting rep confusion and divergent behavior.
- **[Medium] Commissions form and filter demand raw UUIDs** — creating a commission requires pasting a "Sales Order ID" free-text UUID (`sales/commissions/page.tsx:458-463`) and the list filter is "Filter by employee ID…" plain text (lines 267-273), even though the page already loads `employeeOptions` via `useOrgScope` (line 97).
- **[Low] Dead status branch in communication logs** — the badge checks `row.status === 'RESOLVED'` (`communication-logs/page.tsx:236`) but the status enum is `OPEN/FOLLOWED_UP/CLOSED/CANCELLED` (line 29), so the green "resolved" style can never render and CLOSED shows as generic gray.
- **[Low] Sibling inconsistency in entity pickers** — communication-logs' create modal makes users type a raw Entity ID with a hint "Customer / supplier record ID" (`communication-logs/page.tsx:116`), while contact-persons resolves the same concept into a proper customer/supplier dropdown (`contact-persons/page.tsx:96-103`).

### Strengths

- **Mobile POS Lite server-authoritative sale path**: payloads carry only productId/quantity plus an idempotency key; pricing, credit-eligibility, branch scoping, and payment-method enablement are all re-validated server-side (`mobile-pos-lite.service.ts:480-558`), so offline-queued sales can never replay stale prices or duplicate on retry.

- **Frontend/backend permission names align across the CRM suite** (contact_persons, communication_logs, credit_profiles, customer_segments, supplier_performance, customer_statements), so buttons hide exactly where the API would 403 — the commissions module being the lone, critical exception.

## Area: Finance & Accounting

The area is broad and genuinely deep: 14 finance pages (AR/AP with account-grouped views, customer payments with allocation, credit notes, refunds, expenses, intercompany, cash accounts, CoA, fiscal years/periods, journal entries, 12-tab report suite) plus 10 accounting-engine pages (period close, locks, posting rules/runs, bank reconciliations, depreciation, loan repayments, audit adjustments, financial statements, readiness dashboard). The newer pages (customer payments, credit notes) are excellent; however, the area splits into two generations of code, and cross-checking against the NestJS controllers surfaced several verified contract breaks — including edit being broken on eight pages and the refund flow being unusable.

### Findings

- **[Critical] Edit is broken on 8 finance pages (PUT vs PATCH)** — Edit modals send `PUT /:id` (`finance/receivables/page.tsx:961`, `payables/page.tsx:906`, `fiscal-years/page.tsx:54`, `accounting-periods/page.tsx:60`, `journal-entries/page.tsx:184`, `chart-of-accounts/page.tsx:85`, `expenses/page.tsx:152`, `intercompany/page.tsx:98`), but every backend controller registers only `@Patch(':id')` (e.g. `backend/src/modules/receivables/receivables.controller.ts:39`), and the proxy forwards the method verbatim (`frontend/src/app/api/backend/[...path]/route.ts`, `method: req.method`). Every "Save Changes" 404s.
- **[Critical] Refund creation is unusable — credit-note dropdown always empty** — `finance/refunds/page.tsx:144-155` (`parseList`) cannot unwrap the credit-notes list envelope `{ data: { items: [...] } }` (service returns `items`, `credit-notes.service.ts:110-111`; global `TransformInterceptor` wraps in `data`). The required "Credit Note (ISSUED)" select therefore always shows "No ISSUED credit notes", blocking the entire refund workflow. The credit-notes page itself documents this `items` quirk (`credit-notes/page.tsx:121-124`).
- **[Critical] Financial Statements results pane never renders** — `accounting-engine/financial-statements/page.tsx:77-80` requires `resultSummary` to be an array of `{accountId,...}` rows, but the backend stores an object `{ companyId, rows: [{account:{...}}], totalDebit, ... }` (`financial-reports.service.ts:152-159` via `financial-statements.service.ts:78`). Every generated run — including successful trial balances — shows "No account rows were stored for this statement run."
- **[Critical] Fiscal-year / accounting-period Delete hits non-existent endpoints and fails silently** — the pages call `DELETE /fiscal-years/:id` and `/accounting-periods/:id` but neither controller has an `@Delete` route; `DeleteConfirm` never checks `res.ok` (`fiscal-years/page.tsx:83`, `accounting-periods/page.tsx:92`), so the modal closes as if the delete succeeded and the row reappears.
- **[High] Silent-failure pattern on destructive/lifecycle actions** — `DeleteConfirm` in receivables (:1115), payables (:1057), chart-of-accounts (:127), journal-entries (:271), expenses (:205), intercompany (:137) and the fiscal-years/periods close/lock `handleAction` (`fiscal-years/page.tsx:128-134`) never inspect the response; a backend rejection (locked period, FK constraint) is indistinguishable from success.
- **[High] No permission gating on any accounting-engine workflow page** — period-close, posting-runs, posting-rules, bank-reconciliations, depreciation, financial-statements, loan-repayments and audit-adjustments render every mutating control with no `hasPermission` check (contrast every finance page); users without rights see live buttons that fail with raw backend errors.
- **[High] Multi-currency amounts hardcoded to "TZS" in AR/AP** — receivables/payables let you create USD/EUR/KES documents, but list tables and stat cards format everything via `fmtTZS` (`receivables/page.tsx:268-275`, `payables/page.tsx:222-230`) and sum outstanding across currencies into one "TZS" total (`receivables/page.tsx:1218-1227`) — mislabeled and mixed-currency arithmetic.
- **[High] Bank reconciliation is missing its core matching UI** — backend exposes `:id/match`, `:id/unmatch`, `:id/adjustments` (`bank-reconciliations.controller.ts:70-90`) but the page only offers auto "Run Matching", Approve, Close; no manual match/unmatch, no adjustment posting, no statement import (every bank line typed by hand), and Approve is enabled straight from DRAFT even with a nonzero difference (`page.tsx:436-443`).
- **[Medium] Backend capabilities with zero UI surface** — `profit`, `customer-statements`, and `tax-anomaly-detection` modules have no frontend references at all (grep across `frontend/src`); posting-rules backend supports `DELETE /:id` and `GET /:id/lines` but the page offers no delete and no way to view a rule's lines (only a count, `posting-rules/page.tsx:333`), so a misconfigured rule cannot be inspected or removed.
- **[Medium] No expense-category management UI** — `expense-categories` is consumed only as a dropdown in `finance/expenses/page.tsx`; there is no CRUD page anywhere, so the required "Category" select can be permanently empty with no path to fix it in-app.
- **[Medium] Advance-payment contradiction in Receive Payment** — the empty state promises "The full amount will be recorded as an unapplied credit" (`finance/payments/page.tsx:546-551`) but submit requires at least one allocation (`:359-360`) and the backend DTO requires the same — pure customer advances are impossible despite the `unappliedAmount` model and UI copy.
- **[Medium] Period-close checklist is decorative** — the review pane renders hardcoded booleans such as "Backend will block draft journals: true" (`period-close/page.tsx:329-341`) rather than real close-validation data; it looks like control assurance but verifies nothing.
- **[Medium] Raw-UUID form fields instead of pickers** — credit-note create asks for free-text "Sales Order ID" / "Receivable ID" (`credit-notes/page.tsx:620-633`); posting-run create asks for a "Posting Rule ID" and even a user-typed "Error Message" field (`posting-runs/page.tsx:479-507`); cash-account "Linked Bank Account ID" is free text; audit-adjustments reversal uses `window.prompt` (`audit-adjustments/page.tsx:295-296`) while every sibling uses a modal.
- **[Medium] Page-scoped stats presented as global** — journal-entries Draft/Posted/Reversed, expenses statuses, chart-of-accounts "Active", receivables/payables Outstanding/Overdue are computed from the current 20-row page only; payments and credit-notes honestly label "(page)" — the older pages don't, which misleads.
- **[Medium] Group Summary report mislabels debits as income** — `GroupSummaryView` maps `totalDebits`→"Income" and `totalCredits`→"Expenses" columns (`finance/reports/page.tsx:419-422`); also the "JE Drill-down" stat counts journal entry IDs but no actual drill-down navigation exists anywhere in the report suite.
- **[Medium] Accounting-locks page shows raw company UUIDs and off-system styling** — Company column renders `row.companyId` (`accounting-locks/page.tsx:204`) despite having the companies list loaded; hand-rolled `<h1>` header and gray-* palette instead of `PageHeader`/aurora tokens.
- **[Low] AR/AP asymmetry** — receivables accounts view has an "Export Debt PDF" statement button (`receivables/page.tsx:1455-1462`); the payables accounts view has no supplier-statement equivalent (the supplier-statements page lives under CRM with no link from here).
- **[Low] Journal-entries amounts have no currency label at all** — `fmtMoney` (`journal-entries/page.tsx:45-47`) prints bare numbers while sibling pages prefix a currency, inconsistent within the same module.
- **[Low] No pagination on potentially large tables** — cash-accounts, fiscal-years, accounting-periods and all accounting-engine list pages fetch with fixed `limit=100/200` and no pager; large ledgers truncate silently.
- **[Low] Two design-system generations coexist** — payments/credit-notes use `ResponsiveDataTable`, aurora `FormShell`, `api-client` helpers, `PermissionDeniedState` and CSV/PDF export; the other ~18 pages hand-roll tables, raw `fetch`, and duplicate `fmtMoney`/`unwrapList` helpers per file (some import `@/lib/unwrap`, others re-declare it inline).

### Strengths

- The customer-payments allocation flow is genuinely production-grade: oldest-first auto-allocate, per-line outstanding validation mirroring backend rounding, unapplied-credit preview, reversal with mirror-JE messaging, and a server-generated receipt PDF.
- AR/AP detail modals offer real drill-down depth — debtor/creditor identity and credit posture, source documents (sales orders, fuel credit sales, project billings, trips) with product lines, and the full linked journal entry with debit/credit lines.
- Complete state-machine workflows across the board: expenses (draft→submit→approve/reject→pay), intercompany (→post), credit notes (draft→issue→void), refunds (draft→pay→void), audit adjustments (submit→approve→post→reverse), journal entries (post/reverse with reason).
- The report suite is broad: 12 tabs spanning company statements, scope rollup, AR/AP aging, and consolidated group statements with an intercompany-eliminations panel, plus CSV and PDF export.
- The accounting-engine dashboard's finance-readiness scoring (checks, indicators, missing role gaps) is a thoughtful operational surface, and all its action endpoints (`post/reverse/close/reopen/release/generate`) verified as present in the backend controllers.
- Consistent journal-entry balance enforcement in every entry-creating UI (journal entries, audit adjustments both require balanced debit/credit before submit).


## Area: HR

The HR section is the largest in the app: 35 pages covering employees, org structure, contracts, attendance, leave, a Tanzania-specific payroll pipeline (PAYE/NSSF/PSSSF/NHIF/WCF/SDL/HESLB), disputes/CCM, disciplinary, medical exams and statutory reports, backed by a genuinely deep NestJS module. Quality is sharply two-tier: a newer generation of pages (employees, employee detail, disputes, disciplinary, medical exams, leave balances, payslips, statutory reports) is well built and correctly wired, while roughly half the section — the older CRUD pages — is broken at the API contract level: create forms post payloads the backend's strict ValidationPipe (`whitelist + forbidNonWhitelisted`, backend/src/main.ts:56-59) rejects, wrong HTTP methods hit non-existent routes, and nearly all of these pages swallow errors, so failures look like successes. The HR sidebar also references permission codes that don't exist, hiding most of the section from every user.

### Findings

- **[Critical] Most legacy create forms cannot ever succeed — payloads don't match backend DTOs and errors are swallowed** — At least 14 pages post bodies the backend must 400: leave-requests (missing required `leaveRequestNumber`/`companyId`/`createdById`/`totalDays` — companyId is deliberately stripped at page.tsx:59), salary-advances (missing `advanceNumber`/`companyId`/`createdById`, page.tsx:71-78), attendance (`date`/`clockIn`/`status` vs required `attendanceDate`/`clockInTime`/`attendanceStatus`+`attendanceNumber`, page.tsx:99-113), payroll-periods (`code`/`company` vs `payrollPeriodCode`/`companyId`/`createdById`, page.tsx:59-62), payroll-runs (`periodId`/`runType` vs `payrollRunNumber`/`payrollPeriodId`/`companyId`/`createdById`, page.tsx:165-176), employment-contracts (`code`/`company`/`baseSalary` vs `contractCode`/`companyId`/`salaryAmount`/`createdById`, page.tsx:61-64), employee-assignments (sends `company`/`contextType`/`status`, none in DTO; misses required `companyId`/`createdById`), plus leave-types, work-shifts, allowance-types, deduction-types, employee-allowances, employee-deductions, salary-payments, performance, shift-schedules (verified field-by-field against `backend/src/modules/hr/*/dto/create-*.dto.ts`). Every one closes the modal and reloads as if saved. Net effect: the hire→contract→payroll and leave-request workflows cannot be started from the UI at all.
- **[Critical] Leave approval workflow is triply dead** — Requests are created with status `DRAFT` (schema.prisma:8157) and the backend requires `submit` (DRAFT→SUBMITTED) before `approve`, but the UI has no Submit button; Approve/Reject buttons render only for status `'PENDING'`, which is not a value of `LeaveRequestStatus` (leave-requests/page.tsx:110); and they call `POST .../approve|reject` while the backend routes are `@Patch` (page.tsx:68 vs leave-requests.controller.ts:60,80) — a 404 that the page ignores.
- **[Critical] HR sidebar uses permission codes that don't exist, hiding almost the whole section from everyone** — Nav children use `hr.employees.view`, `hr.payroll.view`, `hr.attendance.view`, etc. (frontend/src/components/layout/sidebar.tsx:559-661), but the seed defines `employees.view`, `payroll.view`, `attendance.view`… (database/seeds/seed.ts:147-155, 469-576); `hasPermission` is an exact match (auth-context.tsx:162-166). Only "Dashboard", "Leave Balances" and "Reports" use real codes, so ~20 HR nav items are invisible to every user regardless of role.
- **[Critical] HR Documents page is 100% dead — wrong endpoint path** — All calls go to `/api/backend/hr/hr-documents` (hr-documents/page.tsx:92,107,119) but the controller is `@Controller('hr/documents')` (hr-documents.controller.ts:11); list, create and delete all 404 (list silently renders "No documents"). Its form fields (`category`/`documentRef`/`documentDate`) also don't match the DTO (`documentCategory`/`documentId` required).
- **[High] Wrong HTTP methods break remaining workflow buttons** — Attendance Approve posts `POST :id/approve` vs `@Patch` (attendance/page.tsx:121 vs attendance.controller.ts:39); employment-contract Approve/Terminate use POST vs `@Patch` (employment-contracts/page.tsx:73 vs controller:39,45); salary-payment Reverse uses POST vs `@Patch` (salary-payments/page.tsx:66 vs controller:39). Performance Submit/Approve send `PUT {action}` where `action` isn't a DTO field (performance/page.tsx:75-80) → 400; payroll-period Approve/Close do the same (payroll-periods/page.tsx:69-78). All fail silently.
- **[High] Legacy list pages will crash with real data — relation objects rendered as React children** — Pages type `employee`/`company` as strings but every service returns include objects (`employee: { id, fullName, employeeCode }`); rendering `{lr.employee ?? lr.employeeId}` throws "Objects are not valid as a React child". Affected: leave-requests/page.tsx:103, attendance:208, employment-contracts:111, salary-advances:136, employee-assignments:115-117, payroll-entries:86, and the HR reports tables (reports/page.tsx:39,70,132).
- **[High] Backend termination workflow has no UI surface** — `request-termination`, `approve-termination-hr`, `approve-termination-gm` (employees.controller.ts:74-95) are called nowhere in the frontend (verified by grep). The employee delete dialog even instructs users to "use the termination workflow instead" (employees/page.tsx:625), which doesn't exist in the UI; the only path is directly editing status to TERMINATED in the profile modal.
- **[High] Five-step transfer approval chain has no UI** — `approve-transfer-source-division/target-division/gm/hr/finance` (employee-assignments.controller.ts:54-78) are unreachable; the assignments page shows no transfer state or approval actions, so any assignment entering the transfer flow is stuck.
- **[High] Disciplinary dual sign-off has no UI** — Heavy actions are created as `PENDING_HR_APPROVAL` and need `approve-hr` then `approve-gm` (disciplinary-actions.service.ts:80-190), but the page renders only Edit/Delete (disciplinary-actions/page.tsx:350-357) — suspensions/terminations can never become ACTIVE from the UI.
- **[High] Employee detail: 6 of 9 tabs are placeholders** — Assignments, Contracts, Attendance, Leave, Payroll and Documents tabs show "…will appear here" with a link to the unfiltered global list (employees/[id]/page.tsx:658-699), so there is no per-employee history view anywhere.
- **[High] Raw-UUID inputs in core forms** — New Payroll Run requires typing a "Payroll Period ID" (payroll-runs/page.tsx:415-419), New Leave Request a "Leave Type ID" (leave-requests/page.tsx:137), and the payroll-runs/attendance/payroll-entries filters are free-text ID boxes. Even with the payload bugs fixed, these are unusable for operators.
- **[High] HR Reports page doesn't match backend response shape** — FE expects flat `r.code`/`r.company` and per-employee aggregates (`presentDays`, `approvedDays`), but the service returns `employeeCode` + nested objects and raw attendance rows (hr-reports.service.ts:29-41,58-67); the backend also filters attendance on a nonexistent `date` field (`where.date` vs model `attendanceDate`, hr-reports.service.ts:53-56), which Prisma will reject whenever a date filter is used. No export buttons either.

The "Runs" button on payroll-periods therefore silently shows all runs, unfiltered.
- **[Medium] Silent failure pattern on state-changing actions** — `doAction`-style handlers fire fetch without checking `res.ok` (payroll-runs/page.tsx:202, salary-advances:87, attendance:121, employee-assignments:80, hr-documents:119 and most legacy deletes). A failed payroll calculate/sign-off gives zero feedback; contrast with the correct pattern in disputes/[id]/page.tsx:146-160.
- **[Medium] Missing error/empty-state handling on loads** — hr/page.tsx:82-93 doesn't check `r.ok`, so a 403/500 renders blank stat cards; employees/[id]/page.tsx:215-223 has no catch — a failed load leaves an infinite `PageSpinner`. Legacy lists never use the design system's `error-state`/`empty-state` components.
- **[Medium] Key compliance pages aren't in the nav** — Disputes, disciplinary actions, medical exams, statutory returns and WCF exposure exist only in the command palette (CommandPalette.tsx:293-329); the sidebar HR section and the HR dashboard quick links (hr/page.tsx:61-74) both omit them.

- **[Low] Attendance edit modal is broken on prefill** — `openEdit` puts raw ISO datetimes into `type=date/time` inputs and resets `companyId` to `''`, which empties the required employee select (attendance/page.tsx:86-97).
- **[Low] Unthrottled search** — `PageToolbar` has no debounce (page-toolbar.tsx:41), so the employees list refetches on every keystroke (employees/page.tsx:193-210).

- **Payslip experience is excellent**: bilingual English/Swahili printable payslip with statutory line detail, employer-contribution transparency, print CSS and a run-level payslip summary with totals (payslips/[id]/page.tsx, payroll-runs/[id]/payslips/page.tsx).

- **Good newer-page patterns to standardize on**: leave-balances (pagination, permission-gated allocate/adjust upsert modal with tests), departments/positions/medical-exams (careful payload construction plus `res.ok` error display), and the employees list (ResponsiveDataTable with loading/error/empty states and retry).


## Area: Compliance, Approvals & Security

This area spans ~35 pages: a compliance hub with 19 sub-pages, a 5-page approvals suite, a 6-page security suite, data-isolation (3), and internal-controls (1). Quality is sharply bimodal: the approvals decision flow (`approvals/pending`, `approvals/requests`) and the Tax Cockpit are genuinely polished, and the backend controllers are consistently permission-guarded and scope-aware. But nearly half of the compliance section calls backend routes that have never existed in this repo (the pages fail silently to empty states), the approval engine is wired to nothing, and several pages are stubs or crash on real data. Design-system usage is split between the newer Aurora tokens/components and legacy hardcoded-gray Tailwind tables, often between sibling pages of the same section.

### Findings

- **[Critical] 9 of 20 compliance pages call endpoints that don't exist** — `compliance/tax-authorities`, `tax-types`, `tax-codes`, `tax-rates`, `tax-registrations`, `tax-filing-periods`, `tax-returns`, `tax-transactions`, and `compliance/exports` pages all fetch `/api/backend/compliance/tax-*` (e.g. `compliance/tax-types/page.tsx:130,144`; `tax-returns/page.tsx:50`; `exports/page.tsx:56,113`), but the backend serves these at `tax/types`, `tax/rates`, etc. (`backend/src/modules/tax/*/**.controller.ts:11`) and `data-exports` — no `compliance/tax-*` or `compliance/exports` controller exists anywhere (verified by repo-wide grep; the proxy `frontend/src/app/api/backend/[...path]/route.ts:79` does no rewriting). Verbs mismatch too (frontend `POST :id/approve`, real backend `PATCH`). Git history shows both sides shipped in the initial baseline, so every list renders a false "No … found" empty state (`.catch(() => ({}))`) and every create/edit/delete/post/approve action 404s. The sidebar links all of them (`components/layout/sidebar.tsx:677-773`).

## Area: Cross-Cutting UI Consistency

**Overview:** The app has a genuinely strong shared design system (`frontend/src/components/ui`, 23 primitives with a barrel export) and adoption is broad — 220 of 243 dashboard TSX files import from `@/components/ui`, and the few holdout pages are mostly intentional (standalone mobile-POS, thin record-book wrappers). Dark mode works but leans on a fragile `!important` legacy-class bridge, and the biggest cross-cutting gaps are form-label association in the design system itself, no unsaved-changes protection anywhere, and identical browser-tab titles on ~220 pages.

### Findings

- **[High] Money/date formatting is fragmented across three locales in a financial ERP** — A shared formatter lib exists (`frontend/src/lib/design-system/formatters.ts`: `formatMoney`, `formatDate`, etc.) but only 10 of 243 dashboard files import it, while 177 local `fmt*/formatMoney/fmtDate` helpers are re-declared per page (e.g. `accounting-engine/audit-adjustments/page.tsx:87-91`, `bank-reconciliations/page.tsx:67`). Locale usage splits `'en-GB'` (130 calls), `'en-US'` (70), `'en-TZ'` (51), plus 114 raw `toLocaleString`, 117 `toLocaleDateString`, and 69 `toFixed` — so the same amount/date renders differently between modules, and `en-GB` vs `en-US` date order (03/04 vs 4/3) is genuinely ambiguous for users.
- **[High] The design system's own form labels are not programmatically associated** — `frontend/src/components/ui/forms.tsx:56-70`: `Label` renders a `<label>` with no `htmlFor`, and the input is a sibling inside a nested div, so screen readers announce nothing for `FormInput`/`FormSelect`/`FormTextarea` — used in 126 files. There is also no `aria-invalid`/`aria-describedby` wiring for the error text (`forms.tsx:123`). Compounding it, pages contain 193 raw `<input>` and 234 raw `<select>` elements with only 6 `htmlFor` occurrences in the whole dashboard tree.
- **[High] ConfirmDialog has no focus management, unlike Modal** — `frontend/src/components/ui/modal.tsx:54-101` implements an exemplary focus trap (initial focus, Tab cycling, restore-on-close), but `confirm-dialog.tsx` — the component guarding destructive actions in 52 files — contains zero `focus` calls (only an Escape handler at line 69); `detail-drawer.tsx` likewise. Keyboard focus stays behind the dialog, so a stray Enter can activate the page underneath a delete confirmation.
- **[High] No unsaved-changes protection anywhere** — 0 `beforeunload` handlers and 0 router guards across 54 `onSubmit` forms and large editors (e.g. `operations/_components/order-line-editor.tsx`, `companies/new/page.tsx`). Navigating away from a half-built purchase order or payroll entry silently discards work.
- **[Medium] Native `confirm()`/`alert()` still bypass the design system in 12 files** — 11 `confirm()` calls (`companies/[id]/page.tsx:216,667,688,733`, `settings/page.tsx:328`, `settings/preferences/page.tsx:207`, `users/page.tsx:487`, `group-control/documents/[id]/page.tsx:263`, `settings/number-sequences/page.tsx:184`) and 4 `alert()` calls (`westsides/delivery-notes/page.tsx:434`, `westsides/stock-damage/page.tsx:185`, `users/page.tsx:497`, `hr/employees/[id]/page.tsx:639`) coexist with `ConfirmDialog` (52 files) and `showToast` (69 files) — jarring, unstyled, and blocking.
- **[Medium] ~220 pages share one identical browser-tab title** — Only the root `frontend/src/app/layout.tsx:4` sets `title: 'ITEMBA-R · Group Digital Governance'`; just 5 dashboard files export their own metadata (all mobile-POS), and there are 0 `document.title` writes. Since pages are `'use client'`, every tab, bookmark, and history entry is indistinguishable across ~250 pages.
- **[Medium] Dark mode rides on a ~250-rule `!important` legacy-class bridge** — `frontend/src/styles/globals.css:468-484` documents the compat shim mapping `bg-white`/`text-gray-*`/`bg-red-50` etc. to aurora tokens under `.dark`, explicitly labeled temporary. Even the design system depends on it: `components/ui/btn.tsx:8-13` hardcodes `bg-white text-zinc-700`, `bg-red-600`. Any palette class outside the mapped set silently renders light-mode colors in dark theme, and `!important` makes intentional overrides impossible.
- **[Medium] 35 hand-rolled status-badge color maps duplicate StatusBadge** — Despite `StatusBadge` adoption in 118 files, 35 local `*_COLORS: Record<string,string>` maps with raw palette classes exist (`tasks/page.tsx:7-20`, `api-gateway/logs/page.tsx:18`, `audit-logs/page.tsx:53-60`, `alerts/page.tsx:7`, all `backups/*` pages), so the same status (e.g. CRITICAL, COMPLETED) gets different colors per module and misses the theme-token variants.
- **[Medium] 31 of 174 table files have no horizontal-overflow wrapper — including 9 of 10 integrations pages** — e.g. `integrations/webhooks/page.tsx:90-92` renders `<Card className="overflow-hidden"><table className="w-full">`, so on narrow screens columns squish/clip with no scroll affordance; same in `alerts/`, `background-jobs/`, `roles/page.tsx`, `internal-controls/page.tsx`. There are also 0 mobile card-view alternates (`md:hidden` patterns), so horizontal scroll is the only small-screen strategy — and these 31 files lack even that.
- **[Medium] EmptyState/ErrorState/Skeleton adoption is thin; ~200 pages hand-roll error banners** — `EmptyState` is in 23 files and `ErrorState` in 7, while 203 inline `{error && <div className="...red-50...">}` banners exist (e.g. `accounting-engine/accounting-locks/page.tsx:77`) with per-page wording and spacing variants; the `Skeleton*` family (`components/ui/skeleton.tsx`) is used by 0 dashboard files — dead design-system surface next to 136 files using `PageSpinner`.
- **[Medium] Four pages sit entirely outside the design system** — `audit-logs/page.tsx`, `api-gateway/logs/page.tsx`, `backups/disaster-recovery/page.tsx`, and `document-templates/print-engine/page.tsx` import nothing from `@/components/ui`: hand-rolled headers, `Loading...` text (`api-gateway/logs/page.tsx:72`), and bespoke badges (`audit-logs/page.tsx:53-67`), so these admin surfaces look and behave like a different app (and rely wholly on the dark-mode bridge).
- **[Medium] 1,682 inline `style={{}}` occurrences across 157 files as the primary theming mechanism** — Most set aurora tokens (`style={{ color: 'var(--aurora-text-muted)' }}` — `accounting-engine/audit-adjustments/page.tsx:382` and 40+ siblings per file; top offender `reports/run/page.tsx` with 83). Token-correct but unlintable, unpurgeable, and duplicated per element instead of via the `aurora-*` utility classes globals.css already provides — the codebase mixes three styling idioms (Tailwind classes, aurora utilities, inline token styles) on adjacent lines.
- **[Medium] Feedback pattern is split three ways** — success/error feedback is `showToast` in 69 files, inline `setError` banners in 171 files, and native `alert()` in 4; many mutations show a banner but no toast and vice versa, so users get inconsistent confirmation that a save happened (e.g. `tasks/page.tsx` toasts, `accounting-engine/*` pages banner-only).
- **[Low] Hardcoded hex colors in 14 files** — 72 hex literals, mostly in print/letterhead pages where fixed colors are defensible (`hr/ccm-notices/termination/[employeeId]/page.tsx:156`, `westsides/reports/page.tsx`), but also in screen UI (`finance/_components/ar-ap-detail-ui.tsx:136-140` aging-bucket colors) where dark mode can't adapt them.
- **[Low] Font-size drift: 305 arbitrary `text-[Npx]` values alongside standard scale** — `text-[11px]/[12px]/[13px]` (the kit's own idiom, `btn.tsx:17-20`) mixes with thousands of `text-xs/text-sm` uses, producing 11px vs 12px vs 13px body text on adjacent components with no semantic rule for which applies.
- **[Low] Only one route-level error boundary and zero `loading.tsx` files** — `(dashboard)/error.tsx` is the sole boundary for ~250 pages; a render error anywhere unmounts the whole dashboard shell. Client-side fetch gates make route-level loading files less critical, but section boundaries would contain crashes.
- **[Low] `PermissionGate` is effectively unadopted (2 files)** — permission logic instead flows through `hasPermission`/`usePermission` hooks in 115 files with `PermissionDeniedState` in 10; the pattern is consistent, but the component is dead API surface that invites divergence for new contributors following the barrel export.
- **[Low] aria-label coverage is concentrated in the design system, sparse in pages** — 199 `aria-label`s exist but in only 35 of 243 files; pages that build raw icon-only controls (outside `IconBtn`, which requires a label — `btn.tsx:86`) mostly lack them, though the sweep found few offenders (6 clickable `div/span/tr`s, 0 unlabeled `<img>`).

### Strengths

- **Well-designed, broadly adopted kit:** 220/243 dashboard files import `@/components/ui`; `PageHeader` in 163 files, `Btn` 160, `Modal` 135, `PageSpinner` 136, `StatusBadge` 118 — hand-rolled one-offs are the exception, not the rule, and the barrel export (`components/ui/index.tsx`) even funnels toasts through one import surface.
- **Exemplary a11y where it was engineered:** `Modal` (focus trap, restore, ESC, `aria-modal`/`aria-labelledby` — `modal.tsx:54-122`), `ProductPicker` (full WAI-ARIA combobox with keyboard nav — `product-picker.tsx:157-227`), `ThemeSelector` (radiogroup semantics), toast `aria-live="polite"`.
- **Real three-mode theming with no FOUC:** light/system/dark via `use-theme` + a pre-hydration inline script in `app/layout.tsx` that sets `.dark` before paint; the token system (`--aurora-*`) is comprehensive and the sidebar is deliberately always-dark.
- **Near-universal async-state discipline:** 199/243 files have `catch` blocks, 171 manage error state, 203 render error UI, and 0 fetch-without-catch pages were found — a rarity at this scale.
- **Double-submit protection is the norm:** `Btn loading={}` used 315 times, `ConfirmDialog` has an internal busy state disabling both buttons (`confirm-dialog.tsx:47-125`), plus 52 explicit `disabled={saving}` patterns.
- **Mobile shell works:** the sidebar is a proper mobile drawer (backdrop + `translate-x` + `lg:static`, `components/layout/sidebar.tsx:1171-1180`) with a Topbar hamburger, and 140 dashboard files use responsive breakpoint classes.
