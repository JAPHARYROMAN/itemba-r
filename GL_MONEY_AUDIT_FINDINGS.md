## Details

### 1. [CRITICAL / CONFIRMED] PurchaseOrder.receive() creates a payable and posts a full AP_CONTROL credit, double-counting the liability against the supplier-invoice flow

- **File:** `backend/src/modules/purchase-orders/purchase-orders.service.ts:862`  (area: purchase-orders)
- **Problem:** On a non-CASH purchase, receive() creates its own Payable for existing.totalAmount (lines 862-891) AND posts postPurchaseOrderLedger which debits Inventory/Expense and credits AP_CONTROL for the full totalAmount (lines 893, 1189-1234). The canonical AP in this system comes from the supplier-invoice approve flow, which independently creates a Payable and posts postSupplierInvoicePayable crediting AP_CONTROL at the full invoice amount (supplier-invoices.service.ts lines 340-378, 545-550). The supplier-invoice approve path keys reuse off the *invoice's* own existing.payableId only; it never looks at the PO's payableId, so it does not reuse or net the payable that receive() already created. The GRN flow (goods-received-notes.service.ts) deliberately posts inventory only and NO payable/AP, confirming the intended model is GRN=inventory, SupplierInvoice=AP. receive() conflates both.
- **Failure scenario:** Credit PO for 1,000,000 is CONFIRMED then received via PATCH /:id/receive: receive() debits Inventory 1,000,000 / credits AP_CONTROL 1,000,000 and creates Payable A (outstanding 1,000,000). The supplier later sends an invoice linked to that PO; approving it runs postSupplierInvoicePayable, debiting Inventory 1,000,000 / crediting AP_CONTROL 1,000,000 again and creating Payable B (outstanding 1,000,000). AP_CONTROL and Inventory are each overstated by 1,000,000, supplier balance is double-counted (two open payables), and the company appears to owe the supplier twice for one delivery.
- **Suggested fix:** Pick one liability owner. Either remove payable creation + AP_CONTROL posting from receive() (post only the inventory side, or nothing, and let the supplier invoice own AP), or make the supplier-invoice approve flow detect and reuse an existing PO-linked payable/journal instead of creating a second one. The two paths must not both credit AP_CONTROL for the same goods.

### 2. [CRITICAL / CONFIRMED] cancel() reverses stock and the receivable but never reverses the confirmation journal entry, drifting GL AR/Revenue/COGS

- **File:** `backend/src/modules/sales-orders/sales-orders.service.ts:2338`  (area: sales-orders)
- **Problem:** confirm() always posts a balanced journal via postSalesOrderLedger() (for a CREDIT order: DR AR_CONTROL, CR SALES_REVENUE, CR TAX_VAT_PAYABLE, plus DR COGS / CR INVENTORY_ASSET). cancel() (lines 2338-2403) reverses inventory with a SALES_RETURN movement, sets the linked receivable status='CANCELLED' with outstandingAmount=0, and calls syncCustomerBalance(), then flips the order to CANCELLED. It posts NO reversing journal entry. A grep of the whole service confirms no journal reversal exists in the cancel path (the only 'reverse' references are stock/inventory). The cancel guard at line 2331 only blocks orders that already collected cash (paidAmount>0 or paymentStatus!=UNPAID); an unpaid CONFIRMED CREDIT order passes the guard and is cancellable.
- **Failure scenario:** Confirm a CREDIT sales order with totalAmount=118 (revenue 100, VAT 18) on a stock product with WAC 60/unit, qty 1 (COGS 60). The GL now holds DR AR 118 / CR Revenue 100 / CR VAT 18 and DR COGS 60 / CR Inventory 60. The customer's currentBalance and the receivable both show 118 outstanding. Now cancel the order. Stock is returned (Inventory back to +60) and the receivable/customer balance are zeroed, but the GL still shows AR_CONTROL debited 118, Revenue credited 100, VAT credited 18, and COGS debited 60 with no offsetting Inventory credit reversal pairing. Trial balance AR_CONTROL no longer matches the AR sub-ledger (which is 0), Revenue and output VAT are overstated, and COGS is overstated. Every cancelled confirmed order permanently corrupts the ledger.
- **Suggested fix:** In the cancel() transaction, when existing.status==='CONFIRMED' and a journalEntryId exists, post a reversing journal entry (swap debits/credits of the original confirmation entry, or call a posting-engine reversal) inside the same transaction, exactly as it already reverses inventory. The receivable cancellation and stock return must be accompanied by the GL reversal so AR/Revenue/VAT/COGS unwind together.

### 3. [HIGH / CONFIRMED] Outbound relieves totalValue multiplicatively (newQty * averageCost) instead of additively, so an outbound can INCREASE inventory value when the qty*avg invariant is broken

- **File:** `backend/src/modules/inventory-movements/inventory-movements.service.ts:360`  (area: inventory-movements)
- **Problem:** The outbound branch computes newTotalValue = newQty > 0 ? newQty * newAvgCost : 0. This is a multiplicative re-derivation, directly contradicting the policy comment on lines 343-345 which says outbound must derive totalValue ADDITIVELY (existing total minus removed-at-average). The two formulas are only equal while the invariant totalValue == quantityOnHand * averageCost holds. That invariant is deliberately broken by the cost-less-inbound branch (line 356), which holds totalValue constant while increasing quantityOnHand and leaving averageCost unchanged. Once broken, a partial outbound recomputes value off the (now too-high) averageCost spread over the remaining quantity and can push totalValue ABOVE its pre-outbound level.
- **Failure scenario:** Non-stock / trackInventory:false product P (assertInventoryMovementHasCost returns early so cost is optional, but applyMovementToBalance still maintains a balance row). (1) PURCHASE_RECEIPT 5 units @ unitCost=8 -> cost-bearing inbound: qty=5, averageCost=8, totalValue=40. (2) PURCHASE_RECEIPT 5 units @ unitCost=null -> cost-less inbound branch: qty=10, averageCost stays 8, totalValue HELD at 40 (now 40 != 10*8). (3) SALE_ISSUE 4 units -> outbound: newQty=6, newTotalValue = 6 * 8 = 48. Inventory value rose from 40 to 48 on an OUTBOUND. The additive policy the comment promises would give 40 - 4*8 = 8. The InventoryBalance.totalValue (and thus inventory GL valuation) is now overstated by 40.
- **Suggested fix:** Make outbound match the documented additive policy: newTotalValue = max(0, Number(existing.totalValue) - quantity * newAvgCost) (relieve at the current average), and when newQty reaches 0 force totalValue=0. Do not re-derive value as newQty * averageCost on outbound.

### 4. [HIGH / PLAUSIBLE] Concurrent posting of two GRNs on the same PO bypasses the over-receipt ceiling

- **File:** `backend/src/modules/goods-received-notes/goods-received-notes.service.ts:286`  (area: goods-received-notes)
- **Problem:** post() runs in a $transaction with no explicit isolation level (Postgres default Read Committed) and no FOR UPDATE / SELECT-lock on the purchaseOrder or on the prior-GRN rows. The over-receipt guard derives priorReceivedByProductUnit from a query filtered by status:'POSTED' and id:{not:existing.id}. Two GRNs for the same PO posted concurrently each claim their own row (different ids), and under Read Committed neither transaction sees the other's not-yet-committed POSTED status, so each independently computes prior=0 and passes the ceiling. The PO status updateMany (status in CONFIRMED/PARTIALLY_RECEIVED) does not serialize them either, since both are valid source states.
- **Failure scenario:** PO-1 orders product P unit U qty 10. GRN-A and GRN-B (both APPROVED, each accepting 10 of P:U) are posted at the same instant. Both transactions claim their own GRN, both read prior-received = 0 (other's POSTED row uncommitted), both pass `prior+accepted-ordered = 0+10-10 = 0` and create PURCHASE_RECEIPT movements. Result: 20 units received into inventory against an ordered ceiling of 10 — a silent over-receipt that the guard was meant to prevent.
- **Suggested fix:** Take a row lock on the purchase order at the top of the transaction (e.g. a SELECT ... FOR UPDATE on the PO id, or run post() at Serializable isolation) so concurrent receipts on the same PO are serialized and each sees the other's committed received-to-date before evaluating the ceiling.

### 5. [HIGH / CONFIRMED] runMatch has no status guard, so an already-APPROVED invoice can be reverted to MATCHED/DISPUTED  — FIXED (PR #11)

- **File:** `backend/src/modules/supplier-invoices/supplier-invoices.service.ts:256`  (area: supplier-invoices)
- **Problem:** runMatch() (POST :id/run-match) only checks WRITE access and then calls createThreeWayMatch(), which unconditionally writes supplierInvoice.status = MATCHED or DISPUTED (lines 782-785). There is no check that the invoice is in a pre-approval status. An invoice that has already been APPROVED (payable created, AP journal posted, supplier balance synced) can be flipped back to MATCHED/DISPUTED at any time, and a fresh ThreeWayMatch row is created each call.
- **Failure scenario:** Invoice SI-1 is approved: payable created, AP_CONTROL credited, status=APPROVED. A user calls POST /supplier-invoices/SI-1/run-match. createThreeWayMatch sets status back to MATCHED (or DISPUTED). The invoice now reads as un-approved in lists/reports while a live payable and posted AP journal still exist for it, corrupting the procurement status machine and AP aging. Because MATCHED/DISPUTED are also in approve()'s claimable set, the invoice can then be sent through approve() a second time (creating a duplicate ThreeWayMatch and re-running the payable update path).
- **Suggested fix:** Guard runMatch() (and/or createThreeWayMatch) so matching is only allowed for non-terminal pre-approval statuses (e.g. throw if status is APPROVED/PARTIALLY_PAID/PAID/CANCELLED), mirroring the status whitelist that approve() and update() enforce.

### 6. [HIGH / CONFIRMED] Re-approval recomputes payable.outstandingAmount from the invoice, clobbering payments applied to the payable

- **File:** `backend/src/modules/supplier-invoices/supplier-invoices.service.ts:329`  (area: supplier-invoices)
- **Problem:** On the payable UPDATE branch (existing.payableId set), outstandingAmount is overwritten with new Decimal(existing.totalAmount).minus(existing.paidAmount ?? 0). existing.paidAmount is the SUPPLIER INVOICE's paidAmount, not the payable's. The payable tracks its own paidAmount/outstandingAmount as payments are applied. Recomputing outstanding from the invoice's view ignores any payments booked directly against the payable.
- **Failure scenario:** Invoice approved -> payable PAY-1 created with amount 100, outstanding 100. A 60 payment is applied to PAY-1 (payable.paidAmount=60, outstanding=40), but the invoice row's paidAmount is still 0 (or stale). The invoice is reverted (e.g. via the runMatch hole or a DISPUTED flow) and approve() runs again. The UPDATE branch sets payable.outstandingAmount = 100 - 0 = 100, resurrecting the already-paid 60 as outstanding. syncSupplierBalance then re-aggregates and inflates the supplier's currentBalance by 60.
- **Suggested fix:** On the payable update path, do not overwrite paidAmount/outstandingAmount from the invoice. Either leave them untouched, or derive outstanding from the payable's own paidAmount (amount.minus(payable.paidAmount)), so prior payments against the payable are preserved.

### 7. [HIGH / CONFIRMED] receive() unconditionally re-posts an AP journal even when the PO already has a payable, overwriting the existing journal link and double-crediting AP

- **File:** `backend/src/modules/purchase-orders/purchase-orders.service.ts:893`  (area: purchase-orders)
- **Problem:** receive() reads payableId = existing.payableId ?? null (line 862) and only SKIPS creating a new payable when one exists, but it ALWAYS calls postPurchaseOrderLedger (line 893) which credits AP_CONTROL for the full totalAmount, and then unconditionally overwrites that payable's journalEntryId with the new PO journal (lines 900-904). There is no guard checking whether the existing payable already has a journalEntryId / AP was already posted.
- **Failure scenario:** A supplier invoice is approved first against PO X, creating Payable P (AP_CONTROL credited, P.journalEntryId = JE-invoice) and setting PurchaseOrder.payableId = P. The PO is then received: receive() sees existing.payableId = P, skips payable creation, but still posts a second journal JE-po crediting AP_CONTROL for totalAmount, then sets P.journalEntryId = JE-po. AP_CONTROL is now credited twice for one liability and P points at the PO journal, orphaning the invoice journal in reconciliation.
- **Suggested fix:** Before calling postPurchaseOrderLedger, check whether the linked payable already carries a journalEntryId (or whether a SupplierInvoice journal already exists for this PO) and skip the AP posting in that case; never blindly overwrite payable.journalEntryId.

### 8. [HIGH / CONFIRMED] liveStock criticalCount double-counts every OUT / over-reserved SKU (negative overlaps out and low)

- **File:** `backend/src/modules/inventory-balances/inventory-balances.service.ts:310`  (area: inventory-balances)
- **Problem:** The risk KPI computes `criticalCount: totals.out + totals.low + totals.negative`, but the three counters are not mutually exclusive. `negative` (line 283) increments for any item where `quantityAvailable < 0`, and quantityAvailable = onHand - reserved. Every such item is ALSO already counted in either `out` (status OUT when onHand <= 0, line 280/197) or `low` (status LOW when available <= threshold, which is always true when available < 0, line 281/197). So each negative-available row is added two or three times into criticalCount. The `criticalItems` array right below (line 314) uses an OR filter, so each row appears once there — the count and the list disagree.
- **Failure scenario:** Company has exactly 1 SKU with quantityOnHand=0, quantityReserved=0. status='OUT' so out=1; quantityAvailable=0 is not <0 so negative=0 → criticalCount=1 (OK here). Now a SKU with onHand=5, reserved=8, threshold=10: available=-3 → status='LOW' (low=1) AND negative=1 (available<0) → this single SKU contributes 2 to criticalCount. A dashboard showing '2 critical items' for what is really 1 item; criticalItems list shows 1 entry. Any data-corruption SKU with onHand=-4 (OUT) and available=-4 (negative) contributes out=1 + negative=1 = 2 for one row.
- **Suggested fix:** Count distinct critical rows. Either derive criticalCount from the same predicate used for criticalItems (`annotated.filter(it => it.status !== 'OK' || it.quantityAvailable < 0).length`), or compute a combined flag per item in the reduce and increment one counter, instead of summing the overlapping out+low+negative tallies.

### 9. [HIGH / CONFIRMED] writeOff posts no reversing journal entry: AP_CONTROL stays overstated forever while the subledger drops

- **File:** `backend/src/modules/payables/payables.service.ts:364`  (area: payables-posting)
- **Problem:** writeOff() only flips status to WRITTEN_OFF and stores the reason. It posts NO reversing journal entry, yet the original create()/supplier-invoice flow already debited Expense/Inventory and credited AP_CONTROL for the full amount. After write-off, syncSupplierBalance() (line 619) excludes WRITTEN_OFF from its aggregate, so the supplier subledger (Supplier.currentBalance) and the payable status both report the liability as gone, while the GL AP_CONTROL account still carries the full credit balance. The GL and subledger permanently diverge and AP is overstated.
- **Failure scenario:** Create a payable for 1,000,000 (DR Expense 1,000,000 / CR AP_CONTROL 1,000,000). Supplier.currentBalance = 1,000,000, AP_CONTROL = 1,000,000 credit. Call writeOff(). Now Supplier.currentBalance = 0 and the payable is WRITTEN_OFF, but AP_CONTROL still shows 1,000,000 credit. The balance sheet permanently overstates accounts payable by 1,000,000 with no offsetting entry; a trial balance / AP-aging reconciliation will never tie out.
- **Suggested fix:** Inside the writeOff transaction, post a balanced reversing/derecognition JE (DR AP_CONTROL for the remaining outstandingAmount, CR a write-off income / forgiveness-of-debt account), zero outstandingAmount, and only then sync the supplier balance, so GL AP and the subledger move together.

### 10. [HIGH / CONFIRMED] recordPayment accepts payments against WRITTEN_OFF payables (status-machine hole) and posts a spurious cash JE  — FIXED (PR #11)

- **File:** `backend/src/modules/payables/payables.service.ts:251`  (area: payables-posting)
- **Problem:** recordPayment() locks the row and only validates paymentAmount <= outstandingAmount (line 281). It never checks status. Because writeOff() (line 364) leaves outstandingAmount untouched (it is not zeroed), a WRITTEN_OFF payable still has a positive outstandingAmount, so a payment passes the guard. The method then posts a real settlement JE (DR AP_CONTROL / CR Cash) and flips status to PARTIALLY_PAID/PAID, resurrecting a written-off liability and moving cash out of the ledger.
- **Failure scenario:** Payable of 500,000 is WRITTEN_OFF (status=WRITTEN_OFF, outstandingAmount still 500,000). User calls recordPayment with 500,000. Guard 500,000 <= 500,000 passes, status becomes PAID, and a JE DR AP_CONTROL 500,000 / CR Cash 500,000 is posted — cash is credited (paid out) for a debt that was already forgiven, and the write-off is silently reversed.
- **Suggested fix:** Reject recordPayment when locked.status is WRITTEN_OFF (and arguably PAID), e.g. throw BadRequestException if status not in [OPEN, PARTIALLY_PAID, OVERDUE]; and have writeOff() zero outstandingAmount so the amount can no longer be paid.

### 11. [HIGH / CONFIRMED] Period-close PERIOD_LOCK carries fiscalYearId, so closing one period locks every other open period in the fiscal year

- **File:** `backend/src/common/services/accounting-control.service.ts:87`  (area: accounting-journals)
- **Problem:** assertNoActiveLock builds its scope OR by pushing `{ fiscalYearId: input.fiscalYearId }` whenever the resolved period has a fiscal year (lines 86-88). Period-close's ensurePeriodLock creates a PERIOD_LOCK row with BOTH accountingPeriodId AND fiscalYearId populated (period-close.service.ts lines 181-193, fiscalYearId: close.fiscalYearId). A posting to a *different*, still-OPEN period in the same fiscal year resolves that period and passes its fiscalYearId into assertNoActiveLock; the lock then matches via the `{ fiscalYearId }` branch even though the lock was only meant to freeze the one closed period. The ITMB-048 comment immediately below states the intent is that scoped locks must 'only block their own scope', but the fiscalYearId branch over-matches.
- **Failure scenario:** Company has fiscal year FY-2026 with monthly periods. Accountant closes January via PeriodCloseService.close(); ensurePeriodLock creates an ACTIVE PERIOD_LOCK with accountingPeriodId=jan, fiscalYearId=FY-2026. A user then posts a normal February journal entry (transactionDate 2026-02-15) to the OPEN February period. assertPostingAllowed resolves period=February (fiscalYearId=FY-2026), assertNoActiveLock pushes `{ fiscalYearId: 'FY-2026' }` into scopeOr, the January lock matches on fiscalYearId, and the February posting is rejected with 'Accounting period is locked'. Closing any single month silently freezes the entire fiscal year.
- **Suggested fix:** Only treat a lock as fiscal-year-scoped when it is NOT also period-scoped, mirroring the global-date-window guard. E.g. push `{ accountingPeriodId: null, fiscalYearId: input.fiscalYearId }` instead of `{ fiscalYearId: input.fiscalYearId }`, so a PERIOD_LOCK that names a specific accountingPeriodId only blocks via the exact-period branch and a year-wide lock (no period) still blocks the whole year.

### 12. [HIGH / PLAUSIBLE] reverse() updates the original status unconditionally outside a status guard, allowing a double-reversal race that duplicates the ledger impact

- **File:** `backend/src/modules/journal-entries/journal-entries.service.ts:522`  (area: accounting-journals)
- **Problem:** reverse() reads the original with findOne() OUTSIDE the transaction and checks `original.status === 'POSTED'` (line 467), then inside the $transaction creates the reversal entry and flips the original with a plain `tx.journalEntry.update(... status: 'REVERSED')` (lines 522-530) that has NO `where: { status: 'POSTED' }` guard and does not check an updated count. By contrast post() correctly uses `updateMany({ where: { id, status: 'DRAFT' } })` and asserts count===1 to make the transition atomic. Because there is also no DB unique constraint on reversalOfId (confirmed in schema.prisma), two concurrent reverse() calls on the same POSTED entry both pass the pre-transaction status check and both succeed.
- **Failure scenario:** A posted JE for $1,000 (DR Expense 1000 / CR AP 1000) is reversed twice in quick succession (double-click, retried request, or two operators). Both calls run findOne, both see status=POSTED, both enter their transactions and each creates a reversal entry (DR AP 1000 / CR Expense 1000) with status POSTED, and both set the original to REVERSED. The general ledger now contains TWO $1,000 reversals against a single $1,000 original, net overstating AP/understating expense by $1,000 — an unbalanced economic effect from a duplicated liability reversal.
- **Suggested fix:** Make the original transition atomic and guarded: inside the transaction use `const res = await tx.journalEntry.updateMany({ where: { id: original.id, status: 'POSTED', reversedAt: null }, data: { status: 'REVERSED', ... } })` and throw if `res.count !== 1` so the second concurrent reversal aborts and rolls back its reversal entry. Optionally add a unique partial index on reversalOfId.

### 13. [MEDIUM / PLAUSIBLE] averageCost / totalValue are recomputed as JS floats and written into Decimal columns; the rounded totalValue is then re-read as the additive base on the next inbound, compounding WAC drift

- **File:** `backend/src/modules/inventory-movements/inventory-movements.service.ts:350`  (area: inventory-movements)
