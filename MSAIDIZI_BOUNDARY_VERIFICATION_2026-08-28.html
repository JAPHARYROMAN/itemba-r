Msaidizi Trust Boundaries

Three unbuilt boundaries in the Windows companion — privileged command execution, browser egress, and host file disclosure — read against the code rather than the documentation.

Verdict

All three are genuinely fail-closed. No fail-open path was found: every catch on every traced boundary resolves to refuse, kill switches report “engaged” on unreadable paths, replay stores latch and throw, and unknown outcomes settle as NeedsAttention rather than success.

But in two of the three, the protection described in the documentation is not the protection doing the work — and in one case the documentation states the opposite of what the code does.

What actually holds each boundary

For each boundary: the refusal is real, but it is worth knowing precisely which line would have to change to lift it.

Privileged command execution

Doc contradicts code
Documented
A single always-rejecting gate with no configuration override.
Actual fence
One field initializer in a different service — UnavailableV3SignedDriverAttestationSource — plus the all-zero measurement refusal in RequireReadyHealth.

Browser egress

Strongest of the three
Documented
Refused pending a measured broker and WFP driver.
Actual fence
Four independent layers. The load-bearing one is compile-time: the only shipped posture provider hard-codes a null broker digest, so the capability attestation can never be minted.

Host file disclosure

Doc points at a fixture
Documented
A rejecting “production port” with no configuration switch.
Actual fence
Roughly eleven static predicates scattered across entry points on both sides. The named port is a test fixture that never enters the production object graph.

Findings

Ordered by how badly each would mislead someone hardening or extending this code. None is a live exposure; all are traps laid for the next implementer.

The documentation states the opposite of the code

Corrected
Documented

“The only production gate registered in this repository always rejects and has no configuration override, so no configuration or egress client can enable privileged command launch.”

Verified in code

The DI binding is a factory. The rejecting gate is the fallback; configuration alone selects the named-pipe client, with no source change.

docs/TRUSTED-ROOT.md:74 — claim Program.cs:390-404 — AddSingleton<…Gate>(provider => Create(…, fallback)) Program.cs:414 — return TryCreate(…) ? client! : fallback

Why it matters An operator reading the doc believes configuring the pipe client is impossible. It is not. The real fence lives in a component nobody would think to check, and unlike the factory registration — which the static verifier already pins — nothing guarded it.

A function named “Authorize” authorizes nothing

Renamed
Implied by the name

parseAndAuthorizeEphemeralFileDisclosureGrant establishes that a disclosure grant is authentic and unused.

Verified in code

No signature is verified anywhere in the file, and the nonce is checked for shape only — never consumed. It compares a grant against a binding the caller supplies.

ephemeral-file-disclosure.protocol.ts:106 grep -iE "signature|verify|publicKey|ed25519|p256" → no matches

Why it matters Harmless today — nothing calls it in production. It is a loaded gun for whoever builds the channel: call it, treat “did not throw” as authorized, and the result is a fully replayable disclosure channel. Both the authenticated issuer and the single-consumption nonce ledger are still owed.

The pipeline is ~90% built, and the missing 10% is the safety

Recorded in code
Reads as

An unimplemented feature awaiting a full build, with the unsafe parts simply absent.

Verified in code

Prompt assembly, budgeting and file metadata are all wired. A four-line guard and one stub — sitting beside a fully implemented image equivalent — are what stand between it and a live provider call.

msaidizi-adaptive-reasoning.service.ts:377 — the four-line guard msaidizi-adaptive-reasoning.service.ts:1237 — attachCheckpointFile stub msaidizi-devices.service.ts:5661 — raw bytes, redactionsApplied: false msaidizi-devices.service.ts:5678 — sibling branch DLP-sanitises

Why it matters Deleting the guard and mirroring the image path produces something that compiles, passes the existing tests, and is insecure. Worse, the file branch is already written to skip the DLP scan its sibling branch applies — so the first working implementation would persist unscanned file contents unless that is closed first.

Two implementations of one primitive, at different rigour

Aligned
Egress kill switch

Requires a fully-qualified path and walks the entire ancestor chain for reparse points before believing a marker is absent.

Privileged kill switch

Accepted a relative path and checked only the immediate parent, so a redirect planted higher in the tree could hide the marker.

EgressTrustedKillSwitch.cs — IsPathFullyQualified + ancestor walk TrustedKillSwitch.cs — immediate parent only (now aligned)

Why it matters Both are fail-closed and both were written with care — the doc comment on one states that a missing marker is the only affirmative safe state. But the same idea implemented twice drifted, and only one version got the stronger check. Exploiting it needs write access high in ProgramData, so this is defence in depth, not a hole.

Also recorded

Smaller traps, fixed in place rather than left for a future reader to rediscover.

Dead code that reads like a safeguard

RejectBrowserRegistrationAsync is routed to by nothing — the enforcing refusal is in RegisterBrowserAsync. Marked as not-wired rather than deleted, because it is the only coverage of that error code.

Zero is “refuse” only where it counts

The driver health check treats an all-zero measurement as unprovisioned and refuses. Everywhere else in the managed stack, 64 zeros is an ordinary valid digest — there is no shared non-zero helper, so nothing structurally stops a future digest field being added without the check.

A name stronger than its check

ProbeDriverEnforcement verifies driver health and policy-digest knowledge, not enforcement. Moot today — an ACL mismatch makes the path unreachable — but the name would justify over-claiming later.

How this was checked

Three independent deep reads, then every load-bearing claim re-verified directly at file and line. One earlier claim — that a configuration variable was dead — was wrong and was caught this way, so nothing here rests on a summary alone.

What this means for deployment

The engineering here is careful in a way that is hard to fake. The fail-closed reasoning — a missing marker being the only affirmative safe state, a latch that survives restart, an isolation path strictly stricter than its sibling — is the work of someone thinking properly about trust.

The problem was never that the guards fail. It is that the map did not match the territory: in two of three boundaries the documented protection was decorative and the real protection was incidental — a fallback, a field initializer, a hard-coded null. That is corrected, and the real fences are now pinned by the static verifier.

Recommendation

Do not build these three until the operational ceremonies are done — signing keys, enrolled device identity, live-VM acceptance. Those are human prerequisites no agent can satisfy, and productionDeploymentEligible stays false until they are. What was buildable here was removing the traps that would have made a future implementation dangerous, and that is done.
