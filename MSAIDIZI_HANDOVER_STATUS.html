The honest meaning of “deployed”

This is the one thing worth reading carefully.

Merging to main does not put any of this in front of a user. deploy-production.yml is workflow_dispatch-only and needs an SSH key and protected environment that do not exist yet, and every autonomy switch ships off behind a global kill switch. The ring promotion pipeline additionally demands a signed evidence run and three hand-provisioned digests.

I did not try to work around any of that. Those are the same gates I spent the earlier session verifying are correctly fail-closed, and an agent quietly routing around them would be the single worst outcome available here. So “deployed” means landed on main, with the deploy path itself exercised by CI — the Docker image builds and runtime smoke only run on main, so merging is what proves them.

Before you flip anything on

Check the production .env for MSAIDIZI_CLOUD_ZERO_RETENTION_CONFIRMED. If it is set truthy the backend now refuses to boot by design, pointing you at signed provider-contract evidence instead. Absent or false is fine.

What only you can do

None of this is code. It needs hardware, an organisational identity, or a signature, and no amount of agent time substitutes.

  1. Provision TPM-backed signing keys

    Non-exportable P-256 keys via the Microsoft Platform Crypto Provider, plus the certificate pins in LocalMachine\TrustedPeople. TPM failure stops pairing with no software fallback, by design.

  2. Obtain and use a code-signing certificate

    The installer explicitly does not create or bless production keys. The release scripts must be Authenticode-signed in a controlled ceremony on a Windows 11 + TPM 2.0 host with a disposable guest VM.

  3. Create the protected GitHub environments

    Both msaidizi workflows need protected environments with required reviewers, roughly six secrets, and purpose-separated trust roots. A workflow file cannot configure these.

  4. Produce live-VM acceptance evidence

    Real reboots, real service mutations, kill-switch and rollback drills. The checked-in tests explicitly do not claim this, and productionDeploymentEligible stays false until it exists.

Open, and why I left it

Judgement calls I made rather than defaulting to “do it”.

  • The three trust boundaries. The pipelines behind them are roughly ninety percent built and the missing tenth is the safety — nonce ledger, DLP, streaming transport. Completing them without the acceptance evidence would produce something that compiles, passes the existing tests, and is insecure.
  • CRUD evidence blockers. Fifty-three path-read, four query-read and about twenty-three mutation routes lack executable evidence. Closing them needs a signed evidence run, which is a ceremony, not a code change.
  • Per-run rather than per-session write budgets. I judged this not a defect. The budget is a runaway-loop backstop and that threat genuinely is per-request; a session ceiling belongs in rate limiting.
  • Two structural tidy-ups. msaidizi-memory has no owning module, and one frontend file carries four workspaces at about 4,300 lines. Both are real, neither is a defect, and doing large churn immediately before merging unreviewed code was the wrong trade.

One thing I would not merge on trust

The bulk of this platform was produced by a long autonomous run and, apart from the boundary review, has not been read by a person. It is green, it is fail-closed, and it is coherent — none of which is the same as reviewed. The commits are sliced along clean seams precisely so a human can read them lane by lane rather than facing twelve hundred files at once.
